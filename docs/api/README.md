# Контракты API

[Сервис сценариев](mock-scenarios.openapi.yaml) выгружен из FastAPI при реализации T-120. Файл содержит JSON — допустимый YAML 1.2; отдельная зависимость для сериализации не нужна. Тест `test_scenarios_openapi_matches_saved_contract` сверяет снимок с кодом без подключения к базе.

Изменения T-120: `previewScenario` возвращает `200` с реквизитами и людьми вместо заглушки `501`; в `ScenarioSpec` обязательны `preset` или `company.form` (D-101). T-121 добавляет к результату `tax` и `bankCore`: отчётность, налоговый профиль и обороты/счёт. T-125 подключает БКИ/события, банкротства, ЕИС, блокировки и комплаенс (`bki`, `bankLoans`, `bankSubjects`). БИК берётся из настроек приложения. Схема OpenAPI остаётся прежней; `raw`, общие проверки согласованности и применение относятся к T-126/T-127.

[Коллекция Bruno](collection/mocks/README.md) содержит предпросмотр ООО и ошибку отсутствующей формы. Генератор OpenAPI всех ролей и полная коллекция остаются в плане (T-139 и артефакты сдачи); `make openapi` пока заглушка T-543.

[Снимок схемы api](api.openapi.json) выгружен из запущенного `api` (`curl -s http://127.0.0.1:8100/openapi.json`) при создании каркаса фронта (T-402); в нём `/health/*`, `/auth/*`, `/me`, `/public-config` (состояние после PR #34). По нему orval строит TS-клиент в `web/src/api/generated/` (`pnpm gen:api` в `web/`), а CI-проверка `pnpm gen:api:check` ловит расхождение клиента со снимком. Когда api получит новые ручки, снимок обновляют и перегенерируют клиент одним коммитом; общий `make openapi` остаётся за T-543.

T-371 добавил в снимок `api` ручку `POST /demo/reset` (тег «демо», `operationId: demoReset`), а в снимок сервиса сценариев — `POST /api/v1/scenarios/reset` (часть T-129).

T-220 добавляет `GET /companies/lookup/{inn}` (явное обновление из источников) и `GET /companies/{id}` (кэш карточки до 24 часов). Доступны только свои компании, кроме роли поручителя, либо собственный личный ИНН для поиска связанных компаний и статуса НПД. Лимит — 30 обращений в минуту на сессию. Каждое поле содержит `value`, `source`, `retrievedAt` и `confirmed`; недоступный источник возвращает карточку с неподтверждёнными полями, а не ошибку всей формы. Режим налогообложения подтверждается только при наличии сведений за текущий год. Конвейер решения этот кэш не использует.

В `ApplicationOut` добавлено `companyId`: экран заявки должен загружать карточку именно её компании, даже если клиент переключил активную компанию в другой вкладке. T-417 сохраняет ручные дополнения отдельно в `draft.companyFields` через существующий `PATCH …/draft`; они не заменяют факты источников для кредитного решения.

T-224 добавляет `GET /companies/{id}/gov-contracts`: список ЕИС своей компании (кроме роли поручителя) с номером, заказчиком, предметом, ценой, неоплаченной частью, датой заключения, сроком оплаты и статусом. Выдача по `items`/`nextCursor`, параметры `limit` (1–100, по умолчанию 20), `cursor`, `status`. Порядок — новые даты заключения сверху, затем номер по убыванию; курсор возвращается сервером и передаётся без разбора. Список кэшируется в Redis на один час; `source=EIS` и `retrievedAt` сохраняют происхождение ответа. Сбой кэша не мешает обратиться к источнику; недоступный источник без действующего кэша даёт `503 SERVICE_UNAVAILABLE`. Проверка выбранного контракта в конвейере не использует этот кэш.

T-372 добавляет `POST /demo/personas/{code}/reset`: моки, кэш и данные одной компании, без сброса соседей. Ответ содержит `companyId`, новое `generation`, завершённые шаги, длительность и дату. Идентификатор компании и вход сохраняются. Занятый сбросом/операцией ресурс даёт `409 DEMO_RESET_IN_PROGRESS` с `Retry-After: 1`. Частичный сбой даёт `502 DEMO_RESET_FAILED`, `errors[0].step = MOCKS | CACHE | DATABASE`; изменения этой компании блокируются до успешного повтора. Вне демо-режима — 403, неизвестный код — 404.

T-213: POST /auth/bank-demo-login (только DEMO_MODE) создаёт отдельную sid_bank, по умолчанию UNDERWRITER L2; GET /auth/bank-me возвращает сотрудника и актуальный уровень, POST /auth/bank-logout закрывает только банк. Клиентская cookie и сессия сохраняются. Поле level в запросе запрещено; роль ограничена UNDERWRITER/ADMIN. В UI — одна кнопка андеррайтера.

Банковская очередь T-360: `GET /backoffice/queue`, только `sid_bank` (UNDERWRITER/ADMIN). Параметры `status`, `productCode`, `limit`, `cursor`; ответ `items`/`nextCursor`, старые сверху по моменту входа в текущий статус. По умолчанию MANUAL_REVIEW, автоотказы исключены. Другие статусы показывают историю ручных заявок. Рекомендация и объяснения — из последнего ENGINE-снимка; при отсутствии решения рекомендация null. `documentReceived=null` — сервис документов ещё не подключён. Это отдельная банковская модель; клиентские ответы не расширяются.

Банковская карточка T-361: `GET /backoffice/applications/{id}?expectedVersion=N`, только `sid_bank`. Полные баллы, исходные снимки и внутренние пояснения возвращаются отдельной схемой; клиентская схема не расширяется. `stale=true` сигнализирует об изменении версии; это не блокировка и не разрешение будущей записи. Карточка читается согласованно в REPEATABLE READ/READ ONLY. Пороги — из политики сохранённого решения. `documents=null` означает, что T-332 ещё не подключён.

Статус обслуживания в банковских представлениях: явно заполненное `companies.is_bank_customer` имеет приоритет; при null используется `features.is_bank_customer` последнего ENGINE-снимка, если он известен. false сохраняется как «не клиент», отсутствие обоих значений остаётся null.

В банковском решении `comparisons` содержит пары сумм (`aRub`, `bRub`), год и готовый `deviationPercent` из сохранённых признаков. Фронт не пересчитывает расхождения; исходные features также сохранены для аудита. Клиентская схема не расширяется.
