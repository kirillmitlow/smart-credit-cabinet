## Зачем

Чтобы оба агента (Claude Code и Codex) ставили одни и те же библиотеки одних и тех же версий и не спорили о выборе на ходу. Здесь: что берём, зачем, как фиксируем версии. Чего ещё нет в решениях, вынесено в «Развилки».

## Как фиксируем версии

- **Точные версии записывает не документ, а lock-файл** (файл, где пакетный менеджер запоминает ровно те версии, что поставил). Так сборка у жюри даст то же, что у нас. В документе только «линия» версий.
- Python: `uv` (быстрый менеджер пакетов) → `pyproject.toml` + `uv.lock`; в Dockerfile `uv sync --frozen` (если lock-файл не совпал — сборка падает, а не молча ставит другое).
- Фронт: lock-файл менеджера из Q-049, в Dockerfile установка «по lock-файлу» (`--frozen-lockfile`).
- Версии Python и Node закреплены в файлах `.python-version` и `.nvmrc`, образы Docker — по точному тегу (`python:3.13-slim-bookworm`, не `latest`).
- Агент при первой установке берёт **последние стабильные** версии линии и дальше их не двигает без причины. Обновления зависимостей — отдельным коммитом с прогоном тестов.
- Пакеты в `THIRD_PARTY_NOTICES` попадают скриптом из lock-файлов (требование кейса).

## Развилки для пользователя

**Q-046. Какая версия Python?** Это язык всего бэкенда (api, моки). Сменить потом можно, но дорого: пересборка lock-файлов и поиск несовместимых библиотек.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. 3.12 | Самая «проверенная»: у всех библиотек готовые сборки; поддержка безопасности до осени 2028 | Старше; «нового» ничего не даёт |
| B. 3.13 | Уже зрелая (вышла осенью 2024); поддержка до 2029; готовые сборки есть у большинства библиотек | Мелкие риски у редких пакетов с компилируемой частью |
| C. 3.14 | Самая новая, поддержка до 2030 | Больше всего шансов, что у какой-то библиотеки (ONNX, numpy-сборки и т. п.) нет готовой сборки или есть сюрпризы; на хакатоне без запаса времени |

**Рекомендация: B (3.13)**, с правилом: в первый день `uv lock` и запуск «дымового» теста импортов; если хоть одна нужная библиотека не ставится, откатываемся на 3.12 (меняется одна строка в `.python-version` и Dockerfile). Я не проверял наличие готовых сборок для 3.14 на сегодняшний день: это решается за 10 минут при старте кода. Моки получают ту же версию.

**Q-047. Как `api` и `worker` работают с базой?** Celery-воркер по природе синхронный, FastAPI умеет оба режима. Развилка связана с Q-054 (как воркер ходит в моки).

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. SQLAlchemy 2 **синхронный** (драйвер psycopg 3), эндпоинты `def` | Один стиль кода и в `api`, и в `worker`; те же репозитории; нет ловушек async (ленивая загрузка, привязка к циклу событий); агентам проще | Эндпоинты работают в пуле потоков, не «самая модная» схема. Для нашей нагрузки несущественно |
| B. SQLAlchemy 2 **асинхронный** (asyncpg), как в моках | Единый стиль с моками; «классика» FastAPI | В Celery-задачах нужен `asyncio.run` и свой движок на задачу; две обёртки доступа к БД; частые ошибки у ИИ-агентов (lazy load, закрытые сессии) |
| C. SQLModel (Pydantic + SQLAlchemy в одном классе) | Меньше файлов: модель БД = схема API | Мешает слои (таблица и контракт API не одно и то же), слабее для сложных связей и JSONB, развивается медленнее |

**Рекомендация: A.** Главный риск проекта — время и ошибки агентов, а не производительность: синхронный код в `api` и `worker` общий, значит меньше дублирования и меньше классов ошибок. Асинхронным остаётся только то, что этого требует: SSE и подписка на Redis. Миграции Alembic — в любом варианте.

**Q-048. Чем генерировать TypeScript-клиент из OpenAPI?** Сгенерированный клиент не даёт фронту и бэку разойтись: поменяли поле на бэке — фронт не соберётся.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. orval | Генерирует готовые хуки TanStack Query на каждую ручку; быстро для агентов; зрелый | Много сгенерированного кода; настройка в конфиге |
| B. openapi-typescript + openapi-fetch | Только типы и крошечный клиент, всё прозрачно; нет «магии» | Хуки пишем сами (больше ручного кода и однотипных ошибок) |
| C. hey-api (`openapi-ts`) | Полноценный SDK, плагины (в т. ч. TanStack Query, zod); быстро развивается | Ещё меняется между версиями (риск поломок на ровном месте) |

**Рекомендация: A.** Скорость и меньше ручного кода для агентов важнее прозрачности. Условия: сгенерированное не правим руками; CI перегенерирует клиент и падает, если результат отличается от закоммиченного; `operationId` в FastAPI задаём явно (иначе имена функций получаются нечитаемыми, см. [50-07](07-api-design.md)).

**Q-049. Набор для фронта: роутинг, формы, менеджер пакетов.** React и TanStack Query уже зафиксированы.

| Вариант | Состав | Плюсы | Минусы |
|---|---|---|---|
| A. «Классика» | React Router 7 + react-hook-form + zod + **pnpm** | Самый распространённый набор, много примеров, агенты знают его хорошо. pnpm по умолчанию не запускает чужие скрипты установки (плюс к безопасности) | pnpm нужно поставить (одна команда, версия закреплена в `package.json`) |
| B. Всё от TanStack | TanStack Router + Form + Query + pnpm | Единая экосистема, типобезопасные адреса | Моложе, меньше примеров, выше риск ошибок агентов |
| C. «Минимум» | React Router + формы без библиотеки + **npm** | Ничего дополнительно ставить не надо | Форм много (заявка, согласия, документы): валидацию придётся писать вручную |

**Рекомендация: A.** Форм в продукте много, а `zod` позволяет описать правило проверки один раз и показать ошибку рядом с полем. Если pnpm по какой-то причине мешает (другой ПК у Codex), npm — допустимая замена без других последствий.

**Q-050. Тесты фронта.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Vitest + Testing Library (компоненты) и Playwright (сквозные по персонам на живом compose) | Быстрые мелкие тесты и честная проверка всего пути; Playwright даёт скриншоты и видео для сдачи | Два инструмента; Playwright скачивает браузеры (в CI, не у жюри) |
| B. Только Playwright | Один инструмент | Медленно и грубо ловит ошибки в мелких компонентах |
| C. Cypress | Удобный интерфейс | Тяжелее, медленнее в CI, нет преимуществ над A |

**Рекомендация: A.** Пирамида тестов (70-01): много быстрых, мало сквозных; сквозные прогоняют все 9 персон и заодно служат сценарием самопроверки (D-064).

## Заметки для реализации

- **Лицензия Redis.** Версия 8 вышла под AGPLv3, 7.4 под ограничивающими лицензиями; последняя полностью «свободная» ветка — 7.2. Если это смутит жюри или юристов, образ меняется одной строкой на **Valkey** (свободный форк, команды те же, код не меняется). Решать не нужно, пока вопрос не возник; в `THIRD_PARTY_NOTICES` лицензия образа записывается в любом случае.
- Postgres: образ на Debian (`postgres:17-bookworm`), не Alpine: правильные русские сортировки и меньше сюрпризов.
- ML-пакеты (scikit-learn и другие) не ставим в рабочий образ: это решает «≤ 4 ГБ» (D-066) и уменьшает поверхность атак.
- Мелкие умолчания, которые можно менять без отдельного вопроса: uvicorn без `--reload` в compose; `ruff` с правилами `E,F,I,B,UP,S`; кодировка файлов UTF-8, переводы строк LF.

Выбор этих развилок принят, остальные вопросы документа не закрываются автоматически. Версия библиотеки и совместимость проверяются при разрешённой пробной сборке после одобрения плана.
