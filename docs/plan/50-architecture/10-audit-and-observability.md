Три разных вещи: **аудит** отвечает «кто что сделал и почему», **логи** — «что происходило в программе», **метрики** — «как оно себя чувствует прямо сейчас». Аудит живёт в базе и является частью продукта, остальное — инструменты сопровождения.

## Аудит-лог

Своей новой таблицы аудита мы не заводим: в [06-data-model](06-data-model.md) уже есть две неизменяемые таблицы (`UPDATE` запрещён триггером). Здесь описано, что в них пишется и как это связано с остальным.

| Таблица | Что хранит | Кто пишет |
|---|---|---|
| `application_events` | Всё, что случилось с заявкой: переходы статусов, шаги конвейера, задачи клиенту, ручные решения. Это и **аудит**, и **таймлайн клиента**. `id` последовательный: он же `Last-Event-ID` для живых статусов ([11](11-realtime.md)) | Модуль заявок, в **той же транзакции**, что и смена статуса: нет изменения без записи и записи без изменения |
| `audit_log` | Всё остальное: вход и неудачные входы, смена ролей, действия андеррайтера вне заявки, загрузка и скачивание документов, смена версии правил, `DEMO_RESET` | Модуль `audit`, одной функцией `audit.record(...)` |

Что должно быть в каждой записи (поля 06 уже подходят, ниже требования):

- **Кто:** тип и ID актора (клиент, андеррайтер, система, конвейер), роль. Имён и ИНН целиком нет, только ID и маска.
- **Когда:** время по общим часам стенда (`shared.clock`, `APP_TODAY`), UTC.
- **Что и почему:** тип действия, статус «из → в», код причины. У отклонения от рекомендации ядра причина обязательна ([20-02](../20-process/02-application-states.md)).
- **Связь:** `request_id` ([08](08-integration-adapters.md)) и, где есть, ссылка на решение или снимок.
- **Чего не пишем:** тела документов, коды подписи, персональные данные в `payload`.
- **Таймлайн клиента** — проекция `application_events`: API превращает записи в 6 понятных шагов и тексты ([20-02](../20-process/02-application-states.md)). Внутренние поля (причины скоринга, `payload`) клиенту не отдаются; андеррайтеру и администратору отдаются целиком.
- **Кто читает:** администратор — оба журнала; андеррайтер — события заявки; клиент — свой таймлайн.
- **Очистка.** Журналы чистит только сброс демо: `TRUNCATE` от имени владельца схемы при `DEMO_MODE`, затем первая запись `DEMO_RESET`.
- **Целостность** — Q-066: триггер запрета правок уже есть, как усилить дальше — вопрос пользователю.

## Структурные логи

| Правило | Значение |
|---|---|
| Формат | Одна строка JSON в stdout (Docker собирает сам): `ts`, `level`, `service`, `env`, `event`, `requestId`, `applicationId`, `taskId`, `durationMs` |
| Библиотека | `structlog` (выбрана в [02](02-tech-stack.md)) поверх стандартного `logging`, чтобы библиотеки писали в том же формате |
| Маскирование | Обработчик логов маскирует ИНН и отбрасывает поля с запрещёнными именами (ФИО, счёт, пароль, код, токен) |
| Тела запросов и ответов | Не логируются никогда |
| Уровни | `INFO` по умолчанию, `DEBUG` через `LOG_LEVEL`, без секретов даже на нём |
| Контекст | `requestId`, `applicationId`, пользователь (только ID) подставляются автоматически, не руками |
| Просмотр | `docker compose logs -f api worker`. Сборщик логов (Loki, ELK) не ставим: память |

## Метрики

Формат Prometheus: простой текст на `/metrics`, который может читать любая система мониторинга. Эндпоинт доступен только внутри сети compose и не проходит через публичный прокси.

| Метрика | Что показывает |
|---|---|
| `applications_by_status{status}` | Сколько заявок в каждом из 14 статусов |
| `decisions_total{outcome}` | Решения: одобрено, встречное, отказ, ручное, нужна информация |
| `pipeline_step_duration_seconds{step}` | Длительность шагов конвейера |
| `integration_calls_total{system,result}` | Вызовы внешних систем: успех, ошибка, таймаут, отказ предохранителя |
| `integration_call_duration_seconds{system}` | Длительность вызовов |
| `circuit_breaker_state{system}` | 0 закрыт, 1 полуоткрыт, 2 открыт |
| `outbox_pending{target}`, `outbox_oldest_age_seconds`, `outbox_dead_total` | Очередь сообщений во внешние системы |
| `celery_queue_length{queue}` | Сколько задач ждёт воркера |
| `http_requests_total`, `http_request_duration_seconds` | Запросы к `api` по маршрутам и кодам |
| `sse_connections` | Открытые потоки живых статусов |

**Как собираем.** Воркеры Celery работают несколькими процессами, и метрики из каждого процесса так просто не склеить. Поэтому: статусы, шаги, вызовы и очередь outbox считаются **из таблиц Postgres** обработчиком в `api` в момент опроса (индексы на `status`, `created_at` достаточно для демо); состояние предохранителя читается из Redis; HTTP-метрики и потоки считает сам `api`. Одна точка опроса, ничего не теряется при рестарте воркера. Запасной путь, если упрёмся: режим `prometheus_client multiprocess`.

## Трассировка (OpenTelemetry)

**Трассировка** — рисует путь одного запроса через сервисы с замером каждого участка. Решает Q-064. В MVP путь запроса уже восстанавливается через `X-Request-Id`: по нему в логах, в `integration_calls` и в аудите видна вся цепочка.

## Дашборды (Grafana)

Решает Q-065. В любом варианте без Grafana сохраняется **мини-панель в самом продукте** (демо-панель, 60-05): состояние 4 предохранителей, очередь outbox, число заявок по статусам. Это то, что жюри увидит без запуска дополнительных контейнеров.

## Состояние сервисов

| Эндпоинт | Что проверяет | Кто использует |
|---|---|---|
| `GET /health/live` | Процесс жив | `healthcheck` compose, перезапуск |
| `GET /health/ready` | Postgres отвечает, Redis отвечает, миграции на последней версии | `healthcheck` compose, порядок старта, балансировщик |
| `GET /health/deps` | Информационно: статус четырёх систем, состояние предохранителей, свежесть сигнала воркера | Демо-панель, человек |

Моки **не входят** в `ready`: если БКИ лежит, `api` остаётся рабочим (заявки уходят на ручное рассмотрение). Иначе «уронили БКИ» превратилось бы в «уронили всё».

Воркер: хелсчек по файлу. Сигнал Celery `heartbeat_sent` обновляет файл в `/tmp`; compose проверяет, что ему меньше минуты. Медленная команда `celery inspect ping` не нужна.

## Память: что стоит наблюдаемость

Основной профиль (≤ 4 ГБ, таблица памяти в [01](01-overview.md)) включает только то, что уже внутри `api`: логи, `/metrics`, аудит, демо-панель — это ничего не добавляет по памяти. Остальное в профиле `obs`. В [01](01-overview.md) на `obs` заложено около 150 МБ (с Flower, [05](05-async-processing.md) Q-056); по нашей оценке Prometheus и Grafana вместе дают 250–450 МБ, цифру согласовать после замера.

| Компонент | RAM (оценка, замерить) |
|---|---|
| Prometheus | 100–200 МБ |
| Grafana | 150–250 МБ |
| Jaeger all-in-one (только если Q-064, вариант Б) | 100–200 МБ |

## Развилки для пользователя

### Q-064. Нужна ли распределённая трассировка (OpenTelemetry)

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Нет. Только `X-Request-Id` в логах, журнале и аудите | Ничего лишнего, 0 МБ, 0 ч | Нет красивой диаграммы «где потратили время» |
| Б. Да, OpenTelemetry + Jaeger в профиле `obs` | Наглядная картина запроса `api → worker → мок` | +3–4 ч, +контейнер, больше зависимостей, риск версий |
| В. Код подготовлен, вывод выключен по умолчанию | Можно включить на стенде | Половина работы, пока не нужна |

**Рекомендация: А.** Время лучше уйдёт на тесты и сценарий жюри. В README записать «путь развития: OpenTelemetry», а сквозной ID уже готов к нему.

### Q-065. Нужна ли Grafana

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Нет. Только `/metrics` и демо-панель | Проще, без памяти | Нет «взрослых» дашбордов, жюри видит меньше |
| Б. Да, отдельным профилем `obs` (Prometheus + Grafana с готовым дашбордом из репозитория) | Жюри включает одной командой, на стенде работает всегда; +250–450 МБ только по запросу | +3–4 ч, ещё два образа |
| В. Да, в основном профиле | Всегда видно | Съедает запас до 4 ГБ и дольше стартует у жюри |

**Рекомендация: Б**, делать после сквозного сценария (в MVP это Could). Дашборд «Конвейер и интеграции»: заявки по статусам, ошибки систем, предохранители, очередь outbox. Платим временем в конце.

### Q-066. Насколько защищаем аудит от подделки

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Только то, что уже есть: триггер запрещает `UPDATE`/`DELETE`, у пользователя БД приложения нет прав на удаление | 0 дополнительных часов | Владелец схемы (администратор БД) может поправить записи |
| Б. А + цепочка хешей: каждое событие заявки хранит хеш предыдущего события той же заявки; кнопка «проверить целостность» у администратора | Подделку видно; сильный аргумент для «банковской» разработки | +2–3 ч, два новых столбца в `application_events`, порядок записи в рамках заявки |
| В. Убрать запрет правок | Быстрее всего | Слабая история для критерия «Enterprise» |

**Рекомендация: А сразу, Б после сквозного сценария.** Хеш считается от полей события и хеша предыдущего события той же заявки (цепочка на заявку, а не общая, чтобы записи не вставали в очередь). Тогда в [06](06-data-model.md) добавятся `prev_hash` и `hash`.

## Заметки для реализации

- События заявки пишутся одной функцией модуля заявок, `audit_log` — функцией `audit.record(...)`; обе берут сессию текущей транзакции. Прямой `INSERT` в эти таблицы запрещён тестом, который ищет такие вызовы (границы модулей — [04](04-modules-and-boundaries.md)).
- Подсчёт метрик из базы кэшировать на 5 секунд, чтобы частый опрос не нагружал Postgres.
- Тест маскирования: прогнать набор логов с настоящими на вид ИНН, ФИО и номерами счетов и убедиться, что в выводе их нет.
- Часы стенда (`APP_TODAY`) используются для `ts` аудита, поэтому в демо с подставленной датой журнал согласован с согласиями.
- Правила оповещений не настраиваем. В README перечислить, что бы мы сигналили: предохранитель открыт больше 5 минут, `outbox_dead_total > 0`, самая старая запись outbox старше 10 минут.
