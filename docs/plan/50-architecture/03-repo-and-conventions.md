Агенты сменяют друг друга на разных ПК. Чтобы никто не искал, куда класть файл и как называть, структура и правила фиксируются заранее. Здесь же — что нужно сделать с `AGENTS.md`, когда появится код.

## Структура монорепозитория

Монорепозиторий — одна папка с git, в которой лежит всё: бэкенд, фронт, моки, документы. Так проще передавать смену и одним `docker compose up` собирать целое.

| Путь | Что внутри |
|---|---|
| `/` | `README.md` (для жюри, D-064), `AGENTS.md`, `CLAUDE.md` (уже есть, ссылается на `AGENTS.md`), `docker-compose.yml`, `docker-compose.override.yml` (порты моков, [моки 3.4](../../specs/mocks.md)), `docker-compose.cloud.yml`, `.env.example`, `Makefile`, `.pre-commit-config.yaml`, `.editorconfig`, `THIRD_PARTY_NOTICES.md` |
| `api/` | Бэкенд: `pyproject.toml`, `uv.lock`, `Dockerfile`, `alembic/` (миграции), `policy/` (версионируемые правила `v1.yaml`, D-030), `app/`, `tests/` |
| `api/app/` | `main.py` (приложение FastAPI), `worker.py` (приложение Celery), `shared/` (настройки, часы, ошибки, сессия БД), `modules/<имя>/` (модули из [50-04](04-modules-and-boundaries.md)) |
| `api/app/modules/<имя>/` | Единый набор файлов: `router.py` (REST), `service.py` (сценарии использования), `domain.py` (правила и типы), `repo.py` (работа с БД), `schemas.py` (формы API), `tasks.py` (Celery, если есть) |

| `deploy/` | `db-init/` (SQL создания баз), конфиги nginx, профиль наблюдения, заметки по облачному стенду |

`api/` и `mocks/` — **два независимых Python-проекта** (у каждого свой lock-файл), как задумано в спецификации моков: код моков `api` не импортирует. Общих пакетов между ними нет.

## Именование

| Что | Правило | Пример |
|---|---|---|
| Идентификаторы в коде | Английский | `ApplicationStatus`, `compute_dscr` |
| Python | модули и функции `snake_case`, классы `PascalCase`, константы `UPPER_SNAKE` | `payment_schedule.py` |
| Таблицы БД | множественное число, `snake_case` | `application_events` |
| Поля БД | `snake_case`; внешние ключи `<сущность>_id`; время `*_at`; деньги `*_rub` (целые рубли, как в моках) | `company_id`, `signed_at`, `amount_rub` |
| Перечисления и коды | `UPPER_SNAKE` строкой | `MANUAL_REVIEW`, `DSCR_LOW` |
| JSON в API | `camelCase` (как в моках) | `amountRub` |
| Переменные окружения | `UPPER_SNAKE`, у групп префикс | `MOCK_REGISTRY_URL`, `DEMO_MODE` |
| TypeScript | переменные `camelCase`, компоненты `PascalCase` (файл `ApplicationCard.tsx`), остальные файлы `kebab-case` | `use-application.ts` |
| Ветки | как в протоколе: `plan/<тема>`, `feat/<область>-<тема>`, `fix/…`, `test/…`, `chore/…`, `research/…` | `feat/api-state-machine` |
| Docker | образы `scc-<сервис>`, сервисы compose — как в спецификации моков | `mock-registry` |

**Язык.** Идентификаторы по-английски; комментарии и описания эндпоинтов — по-русски, коротко и «почему», а не «что». Тексты для клиента **не вшиваются в код**: они в словаре формулировок (60-06) и справочнике причин решения (30-12).

## Стиль и проверки

| Область | Инструмент | Правило |
|---|---|---|
| Python: формат и линтер | ruff | Один инструмент. Строка до 100 символов. Наборы правил `E,F,I,B,UP,S,C4,PT` |
| Python: типы | mypy | Строгость — Q-051 |
| Границы модулей | import-linter | Нарушение правила зависимостей ломает CI ([50-04](04-modules-and-boundaries.md)) |
| TypeScript | ESLint + Prettier + `tsc --noEmit` | `strict`, запрет `any` без комментария-причины |
| Миграции | Alembic | Любое изменение моделей = новая миграция в том же коммите; тест «миграции приводят к актуальной схеме» |
| Документы | `scripts/check-docs` | Относительные ссылки живы, шапка есть, mermaid разбирается |

### Хуки до коммита (pre-commit)

Хук запускается автоматически перед `git commit`. Набор: ruff (проверка + формат), prettier и eslint для изменённых файлов фронта, проверка размера файлов (запрет > 1 МБ без причины), конец строки и пробелы, **поиск секретов** (gitleaks), проверка YAML и JSON. Тяжёлое (mypy, тесты, import-linter) не в хуке, а в `make check` и CI, чтобы коммиты не тормозили.

### Команды Makefile (единый вход для обоих агентов)

| Команда | Что делает |
|---|---|
| `make up` / `make down` | Поднять / остановить стенд |
| `make check` | Линтеры, типы, границы модулей, быстрые тесты (то, что должно быть зелёным перед коммитом) |
| `make test` | Все тесты |
| `make fmt` | Автоформат |
| `make openapi` | Выгрузить OpenAPI в `docs/api/` и перегенерировать TS-клиент |
| `make reset` | Сброс демо (`POST /demo/reset`) |

Makefile нужен **только разработчикам**. Жюри пользуется одним `docker compose up` (D-064).

## Коммиты и ветки

- Формат сообщения: `[A] Что сделано` или `[B] Что сделано` (кто сделал — агент A или B, как в протоколе). Сообщение по-английски, одной строкой, в повелительном наклонении, как в текущей истории. Незаконченное: `[A] wip: …`.
- Один коммит — одна логическая вещь; тесты в том же коммите, что и код.
- Изменение контракта (OpenAPI, модель данных, `policy`, статусы заявки) — отдельным коммитом и со ссылкой на решение `D-NNN`.
- В `main` — только через PR с зелёным CI и согласием пользователя (D-00E). Рабочие ветки пушатся при передаче смены.
- Теги: `v0.x` по вехам, `submission` — на момент сдачи (D-001).

## Что должно быть в AGENTS.md, когда появится код

Сейчас `AGENTS.md` описывает процесс планирования. К началу кода в него добавляется **короткий** раздел «Код» (не больше ~30 строк; подробности в этих документах, не копировать):

1. Как поднять стенд и где какой порт (`make up`).
2. Три команды: `make check`, `make test`, `make openapi`.
3. Карта папок на 8 строк (таблица выше, сжатая).
4. Три запрета: не импортировать мимо границ модулей; не править `api/generated`; не менять контракт без решения.
5. «Определение готовности» задачи: зелёный `make check`, тесты на новое поведение, миграция при изменении моделей, обновлённый документ, обновлённый `08-handoff.md`.
6. Ссылка на разделы «Заметки для реализации» документов фазы 4.

`CLAUDE.md` уже подключает `AGENTS.md` одной строкой: оба агента читают одно и то же. Отдельных инструкций «для Claude» и «для Codex» не заводим.

## Развилки для пользователя

**Q-051. Насколько строго проверяем типы Python?** Проверка типов находит ошибки без запуска кода; это особенно полезно, когда код пишет ИИ и его не читает человек-эксперт.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. `mypy --strict` везде | Максимум проверок | Много возни с типами Celery, SQLAlchemy и FastAPI; замедляет агентов |
| B. Строго для ядра (`decisioning`, `simulator`, `pipeline`, `applications`), обычный режим для остального | Строгость там, где цена ошибки выше всего (деньги, статусы); умеренные затраты | Две конфигурации |
| C. Только ruff без проверки типов | Быстрее всего | Теряем целый класс ошибок; слабее для критерия «сопровождение» |

**Рекомендация: B.** Ошибка в расчёте DSCR или в переходе статуса стоит дороже, чем ошибка в служебном роутере. Строгие модули перечислены в `pyproject.toml`; список можно расширять.

## Заметки для реализации

- Первым коммитом кода — каркас: пустые `api/`, `web/`, `deploy/`, Makefile, pre-commit, CI с одним зелёным тестом. Всё остальное ложится в готовые рельсы.
- Файлы больше ~400 строк — сигнал разделить. Исключение: сгенерированное.
- Файл `.env` в git не попадает (уже в `.gitignore`); `.env.example` содержит **только безопасные значения по умолчанию** (локальные ключи моков из спецификации) и комментарии.
- Отдельных `README.md` внутри модулей не заводим: документация живёт в `docs/plan`, а в коде — докстринг в `__init__.py` со ссылкой на нужный документ.
