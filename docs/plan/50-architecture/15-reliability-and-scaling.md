Это история для критерия 05 «Enterprise»: надёжность, отказоустойчивость, масштабирование, сопровождение. Документ собирает в одном месте то, что уже заложено в других, и честно говорит, что упрощено. Новых компонентов здесь нет.

## Принципы

1. **Состояние только в Postgres и Redis.** В процессах `api` и воркера ничего важного не хранится, их можно убить в любой момент.
2. **Postgres — единственный источник правды.** Redis ускоряет и доставляет, но потерянное из него восстанавливается из базы.
3. **Всё, что уходит во внешние системы, идёт через outbox и с ключом идемпотентности.** Сообщение пишется в базу вместе с изменением статуса и доставляется «хотя бы раз»; ключ делает повтор безопасным, то есть выдача происходит «ровно один раз по результату».
4. **Любой шаг конвейера можно выполнить повторно** и получить тот же результат.
5. **Источник упал — заявка не падает**, а уходит на ручное рассмотрение с понятной причиной (раздел 9.3 спецификации моков).

## Что происходит при отказе

| Что упало | Что видит система | Что видит клиент | Как восстанавливается |
|---|---|---|---|
| `mock-registry` / `mock-tax` в автозаполнении | Предохранитель, пустой кэш | Поля вручную, пометка «не подтверждено реестром» | Автоматически, когда мок поднялся |
| `mock-registry` / `mock-tax` в конвейере | После повторов `SourceUnavailable` | `MANUAL_REVIEW`, флаг `SOURCE_UNAVAILABLE` | Андеррайтер нажимает «перепроверить» → `CHECKING` |
| `mock-credit-bureau` в отчёте | То же. Платный запрос не дублируется (ключ) | То же | То же |
| `mock-credit-bureau` в submissions | Сообщение ждёт в outbox | Ничего не заметно | Доставка после возврата, не дольше суток, затем `FAILED` (ручной повтор) |
| `mock-bank-core` обороты | Берём отчётность или выписку | Либо ничего, либо `NEEDS_INFO` | Автоматически |
| `mock-bank-core` выдача | Попытки outbox с тем же ключом, предохранитель | «Выдача в обработке» | Автоматически; в АБС ровно один кредит даже после `LOST_RESPONSE` |
| `postgres` | `/health/ready` отдаёт `503`, запросы — `503` в формате RFC 7807, задачи Celery повторяются с паузой | Страница «сервис временно недоступен» | Контейнер перезапускается, данные в томе. Незакоммиченные операции откатываются целиком |
| `redis` | Нет живых статусов и кэша; предохранитель работает по памяти процесса (Q-061); при сессиях в Redis (Q-062, вариант Б) запросы с сессией отвечают `503`, пока Redis не вернётся | Короткое «сервис временно недоступен», после возврата вход повторять **не** нужно (сессии на диске, AOF) | Перезапуск за секунды. Очередь Celery восстановлена с диска, застрявшие заявки подхватывает «уборщик» (ниже) |
| `api` (1 из 2 и более) | Балансировщик убирает по `ready` | Запрос мог оборваться, клиент повторяет | Остальные экземпляры продолжают, потоки SSE переподключаются |
| `worker` в середине шага | Задача возвращается в очередь (`acks_late`, `reject_on_worker_lost`) | Шаг таймлайна задерживается | Шаг выполняется заново; результат шагов и ключи делают повтор безвредным |
| `beat` | Не идут плановые задачи (сторож, истечение сроков, страховочный запуск outbox) | Ничего в первые минуты | Перезапуск. Всегда один экземпляр |
| Мок вернул не тот формат | `SCHEMA_ERROR`, как недоступность | `MANUAL_REVIEW` | Правка адаптера |
| Заканчивается диск | Не обрабатываем: README просит ≥ 10 ГБ свободно | — | — |

## Деградация

Порядок отказа от функций, когда что-то недоступно: **решение по заявке важнее автозаполнения, автозаполнение важнее «красоты»**.

| Состояние | Что отключается | Что работает |
|---|---|---|
| Реестр или ФНС лежат | Автозаполнение, автоматическое решение | Ручной ввод, ручное рассмотрение |
| БКИ лежит | Автоматическое решение | Автозаполнение, остальные источники, ручное рассмотрение |
| Redis лежит | Сессии (при Q-062 Б), живые статусы, кэш | Публичные страницы; после возврата Redis всё продолжается. Это цена выбора Б; смягчается быстрым перезапуском и сохранением на диск |
| Модель ИИ недоступна | Свободный текст в мастере | Мастер на кнопках (D-060) |
| Воркер остановлен | Продвижение заявок | Заявки накапливаются в `SUBMITTED`, интерфейс работает, после запуска всё обработается |

## Идемпотентность и защита от гонок

| Сценарий | Защита |
|---|---|
| Двойной клик «Отправить» или повтор запроса | `Idempotency-Key` на `POST` (таблица `idempotency_keys`, 50-07) и переход статуса через условное обновление `UPDATE … WHERE id=? AND status=?` (версия заявки растёт). Второй запрос получает `409` либо текущее состояние |
| Две вкладки меняют одну заявку | Оптимистичная блокировка по номеру версии, проигравший получает `409` и обновляет экран |
| Две заявки одной компании | Правило `DUPLICATE_APPLICATION` + уникальное ограничение на уровне базы |
| Повтор шага конвейера | Шаг пишет результат с ключом (заявка, шаг), второй запуск видит запись и пропускает |
| Повтор платного запроса БКИ | Один и тот же `Idempotency-Key` ([08](08-integration-adapters.md)); отчёт переиспользуется в рамках заявки |
| Повтор выдачи | Тот же ключ; мок возвращает сохранённый ответ с `Idempotent-Replayed` |

## Устойчивые фоновые задачи

- **Outbox**: запись пишется в той же транзакции, что и изменение статуса; доставщик выбирает записи через `FOR UPDATE SKIP LOCKED`, несколько воркеров друг другу не мешают. Паузы между попытками растут; после 30 попыток или суток — `FAILED`, видно в демо-панели и метрике, ручной повтор кнопкой ([05](05-async-processing.md)).
- **Сторож** (`pipeline.reaper`, `beat` каждые 30 с, [05](05-async-processing.md)): заявки в `SUBMITTED`/`CHECKING` без живой задачи ставятся в очередь заново; после 5 перезапусков заявка уходит на `MANUAL_REVIEW` с флагом `PIPELINE_ERROR`. Это защита от потери задачи в Redis.
- **Тайм-ауты**: у каждой задачи Celery `soft_time_limit`; зависший вызов не блокирует воркер.
- **Корректная остановка**: воркер дорабатывает текущий шаг, `api` закрывает потоки SSE и ждёт запросы (`--timeout-graceful-shutdown`).

## Масштабирование

Что уже сделано, чтобы запускать несколько экземпляров:

| Что | Как решено | Документ |
|---|---|---|
| Сессии | В Redis (не в памяти процесса) | [09](09-security.md) |
| Кэш и ограничения частоты | В Redis | [08](08-integration-adapters.md) |
| Состояние предохранителей | В Redis | [08](08-integration-adapters.md) |
| Живые статусы | Redis pub/sub + воспроизведение из базы, липкие сессии не нужны | [11](11-realtime.md) |
| Файлы | В Postgres за интерфейсом `FileStore` (в проде — S3) | [12](12-files-and-documents.md) |
| Метрики | Один опрос `api` из базы, не зависит от числа процессов | [10](10-audit-and-observability.md) |
| Миграции | Применяет `api` при старте под блокировкой Postgres, второй экземпляр ждёт | [14](14-deployment.md) |

Как масштабируем:

```bash
docker compose up -d --scale api=2 --scale worker=3
```

(Одна команда в README как демонстрация.) Это работает при условии, что прокси раздаёт запросы между экземплярами `api` (у nginx адрес сервиса нужно переразрешать через `resolver` Docker, иначе он запоминает один экземпляр; проверить при реализации). `beat` не масштабируется, он один. Моки по замыслу — по одному процессу (режим сбоев хранится в памяти), они не наш продукт.

Доказательство для жюри: скрипт нагрузки сначала создаёт 50 разных компаний через `POST /api/v1/scenarios` сервиса сценариев, затем отправляет по одной заявке на компанию параллельно на 2 `api` + 3 воркера, затем проверяет, что у каждой правильный итоговый статус, в АБС по одному кредиту на выданную заявку, в аудите нет дыр. Числа производительности не обещаем: проверяем **корректность** под параллелизмом.

Пределы и дальнейшие шаги: потолок соединений Postgres (размер пула на процесс × число процессов < `max_connections`), в проде перед ним PgBouncer; очереди делятся по назначению (`pipeline`, `outbox`, `documents`), чтобы тяжёлые PDF не мешали конвейеру.

## Обновления без простоя

- **Правило миграций «расширяй — потом сужай»**: новый столбец сначала необязательный, код выкатывается, данные заполняются, обязательность и удаление старого — отдельным релизом. Тогда старая и новая версии `api` одновременно работают с одной схемой.
- Порядок релиза: новый экземпляр `api` (применяет совместимую миграцию под блокировкой) → его `ready` → остановка старых экземпляров → воркеры (дорабатывают текущее и перезапускаются).
- Docker Compose на одном хосте не умеет «плавное обновление» сам; на стенде выполняется вручную по порядку выше. В проде это работа оркестратора (Kubernetes).
- Проверка миграций в CI: чистая база → `alembic upgrade head` → `downgrade` на шаг назад → `upgrade`; плюс тест «модель в коде совпадает с миграциями».

## Что сознательно упрощено

| Упрощение | Что сделали бы в промышленной системе |
|---|---|
| Один Postgres, один Redis, один хост | Кластер Postgres с репликой и автопереключением, Redis Sentinel/Cluster, несколько зон |
| Секреты в переменных окружения | Хранилище секретов (Vault, облачный менеджер), ротация |
| Обмен между сервисами по HTTP внутри сети compose | mTLS между сервисами |
| Антивирус на загрузке не ставим | ClamAV/ICAP-шлюз |
| Логи только в stdout | Централизованный сбор (Loki/ELK), оповещения |
| Нет WAF и защиты от DDoS | WAF на периметре |
| Один экземпляр `beat` | Выбор лидера или планировщик оркестратора |
| Файлы в Postgres | S3-хранилище с шифрованием |
| Синтетические данные, имитация подписи и источников | Реальные интеграции (СМЭВ, БКИ), квалифицированная ЭП |
| Обновление вручную | CI/CD с канареечным выкатом |

## Как это покрывает критерий «Enterprise»

| Тема критерия | Где это видно |
|---|---|
| Безопасность | [09](09-security.md): RBAC, сессии, согласия, OWASP, сканирование в CI |
| Надёжность | Outbox, идемпотентность, сторож, условные обновления |
| Отказоустойчивость | Предохранители, ручное рассмотрение вместо падения, хаос-сценарии. Демо: «уронить БКИ» → заявка идёт на ручное → «починить» → «перепроверить» |

| Сопровождение | Аудит, структурные логи, метрики, миграции без простоя, тесты, ADR, CI |

## Заметки для реализации

- Настройки Celery (`acks_late`, `reject_on_worker_lost`, `visibility_timeout` 15 мин, `prefetch=1`) — в [05](05-async-processing.md), здесь не дублируются.
- Redis: `--appendonly yes --appendfsync everysec`.
- Тесты надёжности как автотесты: убить воркер в середине шага, `LOST_RESPONSE` на выдаче (один кредит), одновременная отправка заявки двумя запросами (один `409`), два экземпляра `api` и событие из воркера.
- Все сценарии из таблицы отказов оформить как строки в сценарии самопроверки жюри (80-07), чтобы они были воспроизводимы кнопками демо-панели.
