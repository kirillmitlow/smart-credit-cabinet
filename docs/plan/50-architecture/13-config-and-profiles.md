Один принцип: **всё, что отличается между ноутбуком, ПК жюри и облаком, задаётся переменными окружения**, а не правкой кода. Запуск без единой настройки (`docker compose up`) обязан работать (RQ-11).

## Принципы

- Настройки читает один класс `Settings` (pydantic-settings), проверяет типы на старте. Ошибка настройки = понятное сообщение при запуске, а не сбой через час.
- Три окружения `APP_ENV`: `local` (по умолчанию, безопасные значения только для разработки), `cloud` (всё обязательное), `test` (для автотестов).
- `.env` в репозиторий не попадает. В репозитории лежит `.env.example`.
- Сборочных переменных у фронтенда нет: он ходит по относительному адресу `/api`. Образ не зависит от стенда (важно для Q-071). Веб-сервер `web` (nginx, [01](01-overview.md)) проксирует `/api` в `api`.

## Переменные окружения

Столбец «по умолч.» — значение на локальном запуске. Пусто значит «нет» (для секретов на `cloud` пусто = обязательно задать).

### Общие

| Имя | Смысл | По умолч. |
|---|---|---|
| `APP_ENV` | `local`, `cloud`, `test` | `local` |
| `APP_TODAY` | «Сегодня» для всего стенда, `ГГГГ-ММ-ДД`; пусто = реальные дата и время (спецификация моков, 2.5) | пусто |

## `.env.example`

Файл лежит в корне, группы совпадают с таблицами выше. Правила: у каждой переменной строка-комментарий «зачем»; секреты помечены «только для разработки»; рядом строка с командой генерации (`openssl rand -hex 24`); значений, похожих на настоящие ключи, нет. Тест проверяет, что **каждая переменная из `Settings` есть в `.env.example`**, и наоборот.

## Профили запуска

| Профиль | Команда | Что включает |
|---|---|---|
| Основной | `docker compose up` | `web`, `api`, `worker`, `beat`, `redis`, `postgres`, `db-init`, 4 мока + `mock-scenarios`. Порты на `127.0.0.1`: `8080` интерфейс, `8000` Swagger `api`, `8101–8105` моки (их публикует `docker-compose.override.yml`, который compose подхватывает сам) |
| Облачный | `docker compose -f docker-compose.yml -f docker-compose.cloud.yml up -d` | Без портов моков и `api`, наружу только прокси на 80/443 с HTTPS, все секреты обязательны (`${VAR:?}`), `APP_ENV=cloud`, `restart: unless-stopped`, лимиты памяти |
| Наблюдаемость | `--profile obs` | Prometheus, Grafana с готовым дашбордом (Q-065), Flower при Q-056 |
| ИИ | `--profile ai` | Контейнер `nlu` с моделью (D-058, модели вшиты в образ; Q-044 в [01](01-overview.md)). Генеративная LLM — профиль `llm` после Q-007 |

Профили складываются: `-f … -f … --profile obs`. Имена профилей (`ai`, `obs`, `llm`) — как в [01](01-overview.md). Файл `docker-compose.override.yml` при явных `-f` не читается, поэтому облако на него не опирается.

## Часы стенда `APP_TODAY`

- Один модуль `shared.clock` (правило R9 в [04](04-modules-and-boundaries.md)). Прямой `datetime.now()` и `date.today()` запрещены правилом линтера (`ruff`, группа `DTZ`). Это касается кода `api`, воркеров, моков.
- Compose передаёт `${APP_TODAY:-}` во все сервисы. Чтобы сменить дату: поменять переменную, перезапустить всё, вызвать `POST /demo/reset`.
- Подпись согласия в `api` и проверка в БКИ видят одно время, потому что читают одну переменную.

## Правила кредитной политики

Правила — не код, а данные (D-030). Решение `decide()` получает правила аргументом и не читает файл.

| Вопрос | Решение |
|---|---|
| Где живут | `policy/v1.yaml` в репозитории: пороги, стоп-факторы, грейды, коридоры ставок, параметры [30-18](../30-decisioning/18-economic-assumptions.md) |
| Проверка | При старте файл проверяется схемой. Невалидный файл = `api` не стартует с понятной ошибкой |
| Версия в базе | Таблица `policy_versions` ([06](06-data-model.md)): номер, хеш (`content_hash`, уникален), полная копия содержимого, `effective_from`. Есть запись с таким хешем — используем, нет — добавляем |
| Что хранит решение | `policy_version_id` (в `decisions`). Старые решения остаются объяснимыми после смены правил |
| Смена правил | Новый файл (`v2.yaml`) + `POLICY_FILE`. Историю даёт git |
| Тесты | Каждый порог в файле имеет тест «чуть ниже / чуть выше»; тест сверяет файл с реестром 30-18 |

## Развилки для пользователя

### Q-070. Можно ли менять правила через интерфейс

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Только файл в репозитории | Минимум кода (0 ч); история в git; жюри не может случайно сломать персон | Нельзя «покрутить порог» на демо |
| Б. Файл + «песочница»: `POST /policy/sandbox` принимает изменённые пороги и пересчитывает **сохранённые** заявки/портфель, **ничего не сохраняя** | Показывает «а что если» (в MVP это Could); боевые правила не трогаются | +4–6 ч, нужен прогон ядра на пачке данных |
| В. Файл + редактирование и активация новой версии через API | Самый «банковский» вид: версионирование, активация, откат | +8–12 ч; жюри может сломать ожидаемые исходы персон; нужен откат к файлу |

**Рекомендация: А для MVP, Б как Could после сквозного сценария и синтетического портфеля.** Б даёт эффект на демо без риска для основного пути. Вариант В не окупается за срок. Платим тем, что до Б нельзя менять правила без перезапуска.

## Заметки для реализации

- Docker Compose подставляет `${VAR:-значение}` только из окружения shell и `.env`; значения по умолчанию в самом compose-файле должны совпадать с `.env.example` (проверка скриптом).
- Группа `x-api-env` (YAML-якорь) общая для `api`, `worker`, `beat`: чтобы переменные не расходились.
- Бэкенд и воркер используют один образ с разными командами. Миграции применяет только `api` при старте под блокировкой Postgres (advisory lock), как решено в [01](01-overview.md); воркер и `beat` ждут готовности `api`.
- Redis: базы 0 (сессии, кэш, ограничения, предохранители) и 1 (очередь) разделены. Если сессии лежат в Redis (Q-062, вариант Б), включается `--appendonly yes` ([05](05-async-processing.md)); в таблице памяти [01](01-overview.md) написано «без сохранения на диск» — синхронизировать.
- Профиль `ai` не должен менять поведение основного: без модели всё работает на кнопках (D-060).
- Список всех переменных с описанием в README генерируется из `Settings`, не пишется руками.
