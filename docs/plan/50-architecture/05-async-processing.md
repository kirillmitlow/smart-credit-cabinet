## Зачем

Конвейер заявки ходит в пять сетевых систем, а они умеют тормозить, падать и терять ответы (режимы chaos моков). Документ описывает, как фоновые задачи устроены так, чтобы заявка **не зависала, не терялась и не выполнялась дважды**: это главный довод для критерия «надёжность».

## Принципы

1. **Postgres — источник правды, Redis — только транспорт.** Потеряли очередь — ничего не потеряно: состояние и «что ещё надо сделать» лежат в базе, а сторож (см. ниже) возвращает потерянное в очередь.
2. **Задача — это «толчок», а не носитель данных.** В очередь кладём только идентификатор (`version_id`), всё остальное задача читает из базы.
3. **Каждая задача безопасна при повторе.** Любую можно выполнить дважды, трижды или оборвать посередине: результат тот же.
4. **Бизнес-сбой — не исключение.** «БКИ не ответил после всех повторов» — это ожидаемый исход (флаг `SOURCE_UNAVAILABLE`, заявка уходит на ручное рассмотрение, [20-01](../20-process/01-process-model.md)). Исключение и повтор на уровне задачи — только для поломок инфраструктуры (БД, Redis).

## Какие задачи есть

| Задача | Очередь | Кто ставит | Что делает | Таймаут |
|---|---|---|---|---|
| `pipeline.run` | `pipeline` | `applications` после отправки заявки или ответа клиента; сторож | Конвейер: проверки → решение → переход статуса | мягкий 60 с, жёсткий 90 с |
| `outbox.relay` | `outbox` | Сразу после коммита (Q-055) и `beat` | Доставляет сообщения в БКИ и АБС | 30 с |
| `pipeline.reaper` («сторож») | `pipeline` | `beat`, каждые 30 с | Находит заявки, у которых задача потерялась или умерла, и ставит её заново | 20 с |
| `applications.expire_overdue` | `default` | `beat`, каждые 60 с | Переводит просроченные задачи клиенту и оферты в `EXPIRED`. **По умолчанию выключена** флагом `EXPIRY_ENABLED=false` | 30 с |
| `documents.parse_statement` | `default` | `documents` после загрузки | Разбор выписки 1С, расчёт оборотов | 60 с |
| `documents.render_contract` | `default` | `offers` при принятии оферты | Генерация договора | 60 с |

Выдача кредита и сообщения в БКИ — не отдельные задачи, а **записи в outbox**, которые доставляет `outbox.relay`.

Один контейнер `worker` слушает три очереди (`-Q pipeline,outbox,default`, 3 процесса). Очереди разделены логически: позже можно вынести `outbox` в отдельный контейнер, ничего не меняя в коде.

## Настройки Celery, которые важны

| Настройка | Значение | Зачем |
|---|---|---|
| Подтверждение «поздно» (`acks_late`) + `reject_on_worker_lost` | включено | Задача считается принятой после выполнения. Умер воркер — сообщение вернётся |
| `worker_prefetch_multiplier` | 1 | Воркер не набирает задач «про запас»: длинная не блокирует очередь |
| `visibility_timeout` брокера Redis | 15 мин (больше любого лимита задачи) | Иначе Redis решит, что задача зависла, и выдаст её второй раз |
| Хранилище результатов (`result_backend`) | **не используем**, `task_ignore_result` | Результат — это запись в базе; экономит память |
| `worker_max_tasks_per_child` | 200 | Страховка от утечек памяти в рамках бюджета ([50-01](01-overview.md)) |
| Сериализация | только JSON | Безопасность: никаких pickle |
| Сохранение Redis на диск (AOF) | для очереди не обязательно | Потеря очереди закрыта сторожем. Если в Redis лежат сессии, сохранение включается ради них (50-09, 50-15) |

## Как устроен конвейер внутри задачи

`pipeline.run` выполняет шаги по порядку. После каждого шага результат **сохраняется в базе** (снимок источника, запись в журнал события заявки). Повторный запуск пропускает уже выполненные шаги.

| Шаг | Что делает | Почему повтор безопасен |
|---|---|---|
| 1. Полнота | Все ли данные и согласия на месте | Только чтение |
| 2. Бесплатные источники (реестр, ЕФРСБ, ФНС, комплаенс, обороты, АБС) | Параллельно до 4 вызовов, снимки в `source_snapshots` | Снимок привязан к версии заявки и шагу: второй запрос заменяет первый, а не дублирует |
| 3. Стоп-факторы по бесплатным данным | `decide()` в режиме «ранний отказ» | Чистая функция |
| 4. БКИ (компания, директор/ИП, поручитель) | `POST credit-reports` с `Idempotency-Key` по заявке и субъекту | Ключ: повтор вернёт тот же отчёт и не создаст платный запрос ([моки, 6.1](../../specs/mocks.md)) |
| 5. Признаки → скоринг → лимиты → ставка → правила | `decide()` | Чистая функция, версия правил записана |
| 6. Сохранение и переход | Запись `decisions`, оферты, переход статуса, события, outbox — **одна транзакция** | Переход «сравнить и поменять» (ниже): второй раз ничего не сделает |

## Как не потерять событие и не выполнить шаг дважды

| Опасность | Защита |
|---|---|
| Статус изменили, а сообщение в БКИ или АБС не записали | **Transactional outbox:** запись в `outbox` в той же транзакции, что и смена статуса. Либо оба, либо ничего |
| Транзакция прошла, а задачу в Redis поставить не успели (упал `api`) | Сторож `pipeline.reaper` раз в 30 с ищет заявки в `SUBMITTED`/`CHECKING` без живой задачи и ставит их заново. То же при потере Redis |
| Задачу доставили дважды | `pipeline_runs` уникальна по версии заявки; задача берёт «аренду» на запуск (`locked_until`, продлевается во время работы). Второй экземпляр видит чужую аренду и тихо выходит |
| Воркер умер посреди конвейера | Аренда истекает → сторож ставит задачу заново → она продолжает **с последнего сохранённого шага** |
| Два процесса одновременно меняют статус | Переход «сравнить и поменять»: `UPDATE … SET status = новый WHERE id = … AND status = старый`. Ноль изменённых строк = кто-то уже сделал, это не ошибка для задачи и `409` для клиента |
| Сообщение в АБС ушло, а ответ потерялся (`LOST_RESPONSE`) | Повтор с **тем же** `Idempotency-Key` (строится из заявки и операции, не случайный) → АБС вернёт сохранённый результат. Деньги не задвоятся. В `disbursements` ещё и уникальность по заявке |
| Сообщения в БКИ приходят не по порядку | Ретранслятор берёт запись, только если нет более ранней неотправленной по тому же `aggregate_id`: `REGISTERED` всегда раньше `DECIDED` |
| Событие SSE потерялось (Redis не гарантирует доставку) | В Redis идёт только «толчок»; клиент при подключении присылает `Last-Event-ID` и дочитывает пропущенное из `application_events` |
| Клиент нажал «отправить» дважды | `Idempotency-Key` на `POST` ([50-07](07-api-design.md)) + запрет перехода `SUBMITTED → SUBMITTED` |

## Повторы: четыре уровня

| Уровень | Что повторяется | Правило |
|---|---|---|
| Адаптер к моку | Один HTTP-вызов | По таблице [моки, 9.2](../../specs/mocks.md): 1–2 повтора, экспонента с разбросом, circuit breaker. После исчерпания — **результат «источник недоступен»**, а не исключение |
| Задача Celery | Вся задача | Только для поломок инфраструктуры (разрыв БД, взаимная блокировка): до 3 раз, паузы 2/10/30 с |
| Outbox | Доставка сообщения | Пока не получится: паузы 5 с → 15 с → 45 с → 2 мин → 5 мин (потолок), с разбросом. После 30 попыток или суток — статус `FAILED`: запись в аудит, видна в демо-панели с кнопкой «повторить» |
| Сторож | Потерянная задача | Каждые 30 с; не более 5 перезапусков одного запуска, затем заявка уходит на `MANUAL_REVIEW` с флагом `PIPELINE_ERROR` |

## Таймеры

Расписание (`beat`): сторож — 30 с; страховочный запуск ретранслятора — 30 с; истечение сроков — 60 с. Сроки (5 дней на ответ клиента, 10 дней на оферту, [20-02](../20-process/02-application-states.md)) лежат в конфиге. **«Сейчас» берётся из `shared.clock`** (`APP_TODAY`), поэтому тест может «перемотать время». На демо-стенде `EXPIRY_ENABLED=false`: заявки жюри не истекают во время проверки.

## Границы

- **Входит:** задачи, очереди, повторы, гарантии доставки.
- **Не входит:** устройство адаптеров и circuit breaker (50-08), содержимое шагов расчёта (30-xx), доставка SSE до браузера (50-11).

## Как проверяем

- Unit: каждый шаг выполняется дважды подряд — одинаковый результат, ровно один побочный эффект.
- Интеграционные (реальные Postgres и Redis, воркер в процессе): убить воркер посреди шага 4 → заявка доезжает до решения; очистить Redis после отправки → сторож возвращает задачу; `LOST_RESPONSE` у АБС → ровно одна выдача; `DOWN` у БКИ → `MANUAL_REVIEW` с `SOURCE_UNAVAILABLE`, воркер жив.
- Property-тест ретранслятора: при любом порядке сбоев сообщения по одной заявке уходят по порядку и без дублей на стороне мока.

## Развилки для пользователя

**Q-053. Как разбит конвейер на задачи Celery?**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Одна задача на запуск, шаги внутри, контрольные точки в БД | Просто читать и отлаживать; одна аренда; не нужен backend результатов | Повтор на уровне шага пишем сами; весь запуск занимает одного исполнителя на 5–20 с |
| B. Цепочка задач Celery (chain/chord), по задаче на шаг | «Родная» схема Celery, повторы по шагам из коробки, видно в Flower | Параллельная группа (chord) требует backend результатов; данные между задачами всё равно через БД; сложнее тестировать |
| C. «Шаг за шагом»: задача делает один шаг и ставит себя на следующий | Каждая задача короткая, прогресс устойчив | Больше обращений к очереди, задержки между шагами, больше кода |

**Рекомендация: A.** Для масштаба прототипа лучший баланс «просто и надёжно»: контрольные точки дают живучесть, а переход к C — механический (функции шагов уже отдельные). B отвергаем из-за chord и backend результатов.

**Q-054. Как задача ходит в моки: синхронно или асинхронно?** Связан с Q-047 (доступ к БД).

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Синхронный httpx; параллельные вызовы через пул потоков (до 4) | Те же адаптеры работают в `api` (автозаполнение) и в `worker`; нет `asyncio` внутри Celery; хватает скорости | Потоки: нужно следить за общим состоянием (circuit breaker держим в Redis) |
| B. `asyncio.run()` в задаче и асинхронный httpx с `gather` | «Модный» стиль, как в моках | Свой цикл событий на задачу, два варианта адаптеров (для `api` и `worker`), типовые ошибки агентов |
| C. Всё последовательно | Проще всего | В плохой день (моки в режиме `SLOW`, 2 повтора) 9 вызовов по 6 с дают ~54 с: не укладываемся в «до минуты» |

**Рекомендация: A.** Параллельные 4 потока сводят худший случай к ~10 с, а один набор адаптеров для всего `api` — меньше кода и ошибок.

**Q-055. Кто запускает ретранслятор outbox?**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. `beat` каждые 5 с | Одна простая вещь | Задержка до 5 с; постоянная работа вхолостую |
| B. Отдельный контейнер с бесконечным циклом и `LISTEN/NOTIFY` Postgres | Мгновенно, элегантно | Ещё один контейнер (+80 МБ), свой код остановки и перезапуска |
| C. «Толчок» `outbox.relay` сразу после коммита + страховка `beat` раз в 30 с | Доставка почти мгновенная; если толчок потерялся, страховка подберёт; контейнеров не добавляем | Два пути запуска (безопасно: записи берутся с блокировкой `SKIP LOCKED`, дубли исключены) |

**Рекомендация: C.** На демо нужны быстрые ответы, а надёжность даёт страховка.

**Q-056. Нужен ли Flower (веб-панель Celery)?**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Нет | Меньше памяти и поверхности атаки | Нечем «показать очередь» жюри |
| B. Только в профиле `obs` (выключен по умолчанию, под паролем) | Есть куда заглянуть на демо; не влияет на основной бюджет | Одна лишняя настройка |
| C. Всегда включён | Всегда под рукой | +150 МБ в основном профиле; панель без защиты — дыра |

**Рекомендация: B.** Для жюри главное видеть **состояние конвейера в самом продукте** (таймлайн, журнал событий); Flower — запас для рассказа об эксплуатации.

## Заметки для реализации

- Задачи объявляем по имени (`pipeline.run`): ставить их можно без импорта модуля `pipeline` (правило R10 в [50-04](04-modules-and-boundaries.md)).
- Постановка задачи — **после коммита** (хук `after_commit`). Постановка до коммита — классическая ошибка: воркер стартует раньше, чем данные видны.
- Сторож и сроки считают время по `shared.clock`, а «зависшим» запуск считается по настоящему времени (`locked_until`): это системное время, не `APP_TODAY`.
- Все задачи пишут `requestId` и `applicationId` в лог; `requestId` кладётся в заголовок задачи при постановке, чтобы трассировать путь «клик → воркер → мок».
- Circuit breaker между процессами должен делить состояние: либо Redis, либо (проще) каждый процесс держит своё. Решает 50-08 (Q-061). Документ 50-08 пока описывает адаптеры как `async` (вариант B из Q-054); если выбран вариант A, его раздел про httpx и `asyncio.run` приводится к синхронному виду.
