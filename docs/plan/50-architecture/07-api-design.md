## Зачем

Единые правила для всех ручек `api`, чтобы фронт, тесты и жюри видели предсказуемый интерфейс, а оба агента не изобретали каждый своё. Правила сознательно **повторяют соглашения моков** (спецификация, раздел 2): жюри увидит один стиль во всей системе.

## Соглашения

| Тема | Правило |
|---|---|
| Базовый путь и версия | `/api/v1`. Версия в пути. Добавление полей и ручек версию не меняет; удаление и смена смысла = `/api/v2`. Поля внутри `v1` не удаляем. Критичное изменение ловит сравнение OpenAPI в CI (инструмент `oasdiff`) |
| Формат | JSON, UTF-8, `camelCase` (в Pydantic через `alias_generator`) |
| Время, деньги, проценты | Даты `2026-10-20`, моменты `2026-10-20T09:12:00Z` (UTC); деньги — целые рубли в полях `*Rub`; проценты — `ratePercent: 21.5` |
| Перечисления, отсутствие значения | `UPPER_SNAKE_CASE`; отсутствующее значение — явный `null`, поле не пропускаем (схема стабильна) |
| Адреса | Существительные во множественном числе, вложенность не глубже двух уровней: `/applications/{id}/tasks`. Действия, которые меняют состояние, — `POST` на подресурс-глагол: `/applications/{id}/submit`, `/offers/{id}/accept`, `/contracts/{id}/sign`. Они не CRUD, а переходы стейт-машины (D-055) |
| Идентификаторы | UUID ([50-06](06-data-model.md)); в пользовательских экранах показываем `number` заявки |
| Доступ | Текущий пользователь определяется сессией (способ — 50-09, Q-035). Чужая компания → **`404`**, а не `403`: не подсказываем, что объект существует |
| Заголовки | `X-Instance-Id` возвращаем как непрозрачный ID процесса `api` (проверка балансировки); `X-Request-Id` принимаем и возвращаем (сквозной, попадает в логи, [моки, 2.3](../../specs/mocks.md)); `Idempotency-Key` — для `POST`; `Retry-After` — для `429`, `503`, `409 IDEMPOTENCY_IN_PROGRESS` |
| Длинные операции | Не держим соединение: `POST …/submit` отвечает сразу (`200` с новым статусом `SUBMITTED`), дальше прогресс в SSE (`GET /api/v1/events/stream`, 50-11) и в `GET …/timeline` |
| Файлы | Загрузка — `multipart/form-data`, лимит размера и список типов в настройках (50-12); скачивание — `Content-Disposition` |
| CORS | Не нужен: браузер ходит на один адрес `web`, который проксирует `/api` ([50-01](01-overview.md)) |
| Ограничение частоты | `429` + `Retry-After` на вход и на демо-эндпоинты (50-09) |

### Ошибки (RFC 7807)

Все ошибки — `application/problem+json`, та же форма, что в моках ([моки, 2.4](../../specs/mocks.md)): `type`, `title`, `status`, **`code`** (машинное, `UPPER_SNAKE`), `detail`, `requestId`, при проверке полей — `errors[]` с путём к полю. Клиентский текст ошибки берётся фронтом из словаря по `code` (60-06), а не из `detail`.

| HTTP | Когда | Примеры `code` |
|---|---|---|
| 400 | Запрос разобрать нельзя | `BAD_REQUEST`, `INN_INVALID` |
| 401 / 403 | Нет сессии / нет права | `UNAUTHENTICATED`, `ROLE_CANNOT_SIGN` (бухгалтер пытается подписать), `DEMO_MODE_DISABLED` |
| 404 | Нет объекта или он чужой | `NOT_FOUND` |
| 409 | Конфликт состояния | `INVALID_TRANSITION` (с полем `currentStatus`), `VERSION_CONFLICT` (черновик изменили в другой вкладке), `DUPLICATE_APPLICATION`, `IDEMPOTENCY_IN_PROGRESS`, `IDEMPOTENCY_KEY_REUSED` |
| 422 | Данные разобраны, но не проходят проверку | `VALIDATION_ERROR`, `CONSENT_REQUIRED` |
| 429 / 503 | Лимит / временная недоступность | `RATE_LIMITED`, `SERVICE_UNAVAILABLE` |

### Идемпотентность `POST`

Идемпотентность — повтор того же запроса не создаёт второго эффекта (двойное нажатие, обрыв сети).

- Обязателен `Idempotency-Key` для `POST`, меняющих состояние: отправка, отзыв, принятие оферты, подпись, загрузка документа, ответ на задачу. Фронт создаёт ключ на **действие пользователя** и при повторе отправляет тот же.
- Область ключа: пользователь + метод + путь. Тот же ключ и тот же запрос → вернуть сохранённый ответ с `Idempotent-Replayed: true`. Тот же ключ и другое тело → `409 IDEMPOTENCY_KEY_REUSED`. Запрос ещё выполняется → `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After`.
- Сохраняем только ответы `2xx`; срок хранения — сутки; таблица `idempotency_keys` ([50-06](06-data-model.md)). Правила те же, что у моков (D-078).
- Дополнительная страховка от двойной отправки: сам переход `SUBMITTED → SUBMITTED` запрещён стейт-машиной.
- Автосохранение черновика (`PATCH`) защищено другим способом: клиент шлёт `version`, при расхождении `409 VERSION_CONFLICT`.

### Списки и пагинация

Списки возвращают `{ "items": [...], "nextCursor": "..." | null }`. Курсор — непрозрачная строка; параметры `limit` (по умолчанию 20, максимум 100) и `cursor`. Порядок фиксирован (новые сверху), параметров сортировки нет. Фильтры — простые поля: `status`, `companyId`. Списки одной компании маленькие, но правило единое.

### Разные представления одного объекта

Клиент и андеррайтер видят **разные схемы** одного решения. Клиенту — исход, понятные причины и «что сделать»; баллы, грейд, `pd` и снимки источников — только роли `UNDERWRITER`. Это отдельные модели ответа, а не «скрыть поля на фронте».

## OpenAPI и клиент для фронта

Схема OpenAPI — главный контракт между `api`, `web` и тестами. Сквозной путь:

1. FastAPI строит схему из кода. Теги = модули; `operationId` задаётся единым правилом `<ресурс><Действие>` (например, `applicationsSubmit`), иначе генераторы выдают нечитаемые имена.
2. `make openapi` выгружает схему в `docs/api/api.openapi.yaml` (рядом `mock-*.openapi.yaml` из моков) и перегенерирует TS-клиент в `web/src/api/generated/` (инструмент — Q-048).
3. CI: выгрузка совпадает с закоммиченной; клиент совпадает со схемой; нет критичных изменений относительно `main`; схема проходит линтер правил (Spectral: все ручки имеют `operationId`, ответы ошибок описаны, имена полей `camelCase`).
4. Коллекция запросов для жюри (формат — Postman или Bruno) собирается из схемы и дополняется папкой «Сценарий самопроверки по персонам»; лежит в `docs/api/`.
5. Контрактные тесты (70-04): автоматические проверки ручек по схеме (Schemathesis) и тест «ответ соответствует схеме» на каждый сценарий персоны.

## Границы

- **Входит:** соглашения, список ручек верхнего уровня, путь схемы до клиента.
- **Не входит:** схемы полей каждой ручки (их задаёт код и схема), способ входа и сессии (50-09), протокол SSE (50-11), адаптеры к моквам (50-08).

## Как проверяем

- Каждая ручка из таблиц есть в выгруженной схеме (тест перечня).
- Единый тест ошибок: любая ошибка = `problem+json` с `code` и `requestId`.
- Тесты идемпотентности: повтор, расхождение тела, параллельный повтор.
- Тест «чужая компания → 404» на каждый ресурс с `companyId`.
- Тест стейт-машины на уровне API: недопустимый переход = `409 INVALID_TRANSITION`.

## Развилки для пользователя

**Q-059. Откуда берётся схема OpenAPI: из кода или пишем вручную первой?**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. **Код первичен** (code-first): FastAPI строит схему сам; CI проверяет, что выгрузка в `docs/api/` не устарела; контрактные тесты и линтер Spectral держат качество | Один источник правды; расхождение «схема ≠ код» невозможно; быстрее для агентов; так же сделаны моки | Схему нельзя утвердить до написания кода; качество описаний зависит от аннотаций в коде |
| B. **Схема первична** (spec-first): вручную пишем YAML, по нему сверяем код | Можно утвердить контракт заранее и показать фронту | Дублирование: схему пишем руками (сотни строк YAML), легко расходится с кодом; больше работы агентам |
| C. Гибрид: ключевые ручки (заявка, решение, оферта) сначала описываем таблицами в документах (как здесь), остальное — как A | Контракт на главное согласован до кода, лишней работы нет | Две формы описания для части ручек |

**Рекомендация: A**, а роль «согласованного контракта до кода» уже играет эта таблица ручек и документы 20-02, 50-06. Платим тем, что точные поля увидим уже в Swagger, а не в отдельном YAML-плане.

## Заметки для реализации

- Модели ответа для клиента и андеррайтера разделять сразу, не «потом»: иначе в клиентский ответ попадут внутренности скоринга.
- Для `POST …/submit` и других переходов возвращать обновлённую заявку с `status` и `allowedActions` (что можно сделать дальше): фронт строит кнопки по ним, а не по своей копии стейт-машины.
- Тексты ошибок для людей не вшиваются в `detail`: фронт переводит `code` через словарь. `detail` — для разработчика.
- Предпочесть `def`-эндпоинты (синхронный стиль, Q-047). Асинхронны только `GET /events/stream` и ручки, которые тянут Redis.
- Для `GET /companies/lookup/{inn}` в ответе у каждого поля `source` и `retrievedAt`; сбой источника отдаёт карточку с пометкой `UNCONFIRMED`, а не ошибку (поведение из [20-01](../20-process/01-process-model.md)).

**Уточнение входа, C-14:** код показывается только в демо-режиме. `roles` не создаёт сессию; подтверждение кода обязательно. Ограничение частоты — по ИНН и IP (50-09). Выбор пользователя компании не даёт права подписывать за другого человека. Два контекста сессии — D-085; для SSE `zone=client|bank` выбирает контекст, но не заменяет серверную проверку роли.

**Ручной вариант андеррайтера (D-086, Q-088):** `POST /backoffice/applications/{id}/evaluate-offer` принимает продукт, сумму, срок, ставку и версию заявки; возвращает расчёт, допустимость, нарушения и requiredLevel без изменения статуса. `decision` принимает ссылку на проверенный вариант и версию, повторно проверяет ограничения и сохраняет снимок. Устаревшие данные → 409 VERSION_CONFLICT. Ручной пересчёт использует те же функции математики и политики, что автомат; право L2 не снимает жёсткие запреты 30-11.
