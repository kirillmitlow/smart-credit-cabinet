## Тонкий слой B

1. Авторизация через актуальный auth.BankPrincipal, отдельная банковская cookie и CSRF. Уровень брать из Principal, не из тела запроса. ADMIN не превращает L1 в L2; матрицу проверяет ядро.
2. Проверка версии заявки обязательна на сервере. Для решения передавать также ссылку на ENGINE-снимок из карточки. Старую карточку не адаптировать молча к новым данным.
3. Изменяющие POST оградить от общего/персонального сброса через существующий OperationFence. Найти компанию по публичному applications.operation_scope; не обновлять applications/decisions напрямую.
4. Идемпотентность — shared.idempotency.run_once, область включает пользователя, действие и application_id; хэшировать всё значимое тело. Успешный ответ, аудит B и вызов порта A — одна транзакция. Повтор после потерянного ответа возвращает сохранённый результат, не создаёт второй снимок, offer или pipeline run.
5. Переход статуса, событие и offer не повторять: ими владеет record_underwriter_decision. Перепроверка сама создаёт run, событие и enqueue после commit; B не вызывает pipeline.run дополнительно.
6. Отказ AUTHORITY_LEVEL_TOO_LOW: дождаться отката основной транзакции, затем сохранить аудит попытки отдельной транзакцией. Иначе журнал отказа тоже откатится. Не считать отказ успешным идемпотентным результатом.
7. Модели банка отделены от клиентских. Комментарий сотрудника не включать в клиентский ответ/событие/объяснение, использовать понятные клиентские тексты владельца решения.

## Что важно в портах A

record принимает Session вызывающего, application_id, expected_version, actor_id, actor_level, outcome, terms, reason_code, comment и engine_decision_id. Возвращает UnderwriterReceipt: decision_id, исходный ENGINE, новый статус/версию, deviation/exception, offer_id и evaluation. APPROVED требует исходные продукт/сумму/срок; иные условия — COUNTER_OFFER. Для одобрения/встречного terms обязательны; отказ не принимает terms. Ставка в UnderwriterTerms — доля, а не проценты; явно преобразовать на границе HTTP, считать только Decimal.

preview не пишет данные. Возвращает допустимость, нарушения, платёж, DSCR/стресс, коридор, requiredLevel, inputs_hash/policy_hash/версию. Для T-364 ссылка на проверенный вариант и привязка к исходным данным должны проверяться сервером; повторный расчёт при сохранении обязателен. Способ хранения ссылки — деталь B, выбрать после чтения финального порта, не доверять расчёту из браузера.

request_recheck принимает Session, application_id, expected_version, Actor и actor_id, необязательные reason_code/version_reason/data_patch. Для банковской перепроверки — Actor.UNDERWRITER, текущая версия без правок клиентских ответов. Он возвращает run_id/run_key, версию снимка и application_version после CHECKING. Старый ключ уже DONE: обычный enqueue прежнего pipeline.run не заменяет этот порт.

## Минимальные проверки B

- Банковская сессия действует; клиентская cookie, отсутствие CSRF и подмена actor/level не дают выполнить действие.
- MANUAL_REVIEW → ручное решение создаёт ровно один снимок/переход/offer. Повтор с тем же ключом даёт тот же результат; другое тело с тем же ключом —409.
- Устаревшая версия/ENGINE-снимок —409, никаких частичных изменений. L1 на сумму L2 —403 и устойчивый аудит. Стоп-фактор не снимается.
- Отказ вместо рекомендации «одобрить» без причины не проходит; с допустимой причиной/комментарием появляется история. В клиентском ответе комментария нет.
- Откат транзакции убирает снимок, события, offer и идемпотентный успех. Для recheck откат не оставляет run и не ставит задачу.
- Одновременные решение/перепроверка/сброс не создают два результата и не оживляют сброшенную компанию.
- Ручная проверка условий совпадает с ядром; ставка передаётся без потери точности. Проверенный вариант нельзя сохранить на другой версии заявки.
- Браузер: Станкопром → ручное рассмотрение → запрос сведений → ответ клиента → перепроверка → ручное одобрение. До T-350/T-351 этот полный путь остаётся незавершённым.
