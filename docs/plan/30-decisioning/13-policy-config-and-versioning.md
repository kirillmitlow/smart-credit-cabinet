## Зачем

Все пороги, баллы и ставки лежат в одном файле, а не в коде. Это даёт три вещи: риск-менеджер меняет правила без программиста, каждое решение привязано к версии правил, любое решение можно **пересчитать** и получить тот же результат.

## Что лежит в конфиге

Файл `policy/vN.yaml` (формат не описываем: структура ниже). У **каждого числа** три поля: значение, `source` (номер в 30-18, решение `D-NNN` или `допущение: …`) и короткий комментарий. Файл без `source` у числа не проходит проверку.

| Раздел | Что внутри | Документ |
|---|---|---|
| `meta` | Номер версии, дата вступления, описание изменений, дата ключевой ставки | — |
| `catalog` | 6 продуктов: границы суммы и срока, вид погашения, порог залога, требования (возраст, клиент банка, контракт), базовая ставка, коридор, надбавка на расходы, авто-лимиты (грейд B и A), допустимые грейды, нужные документы | 10-06, 30-11 |

| `stop_factors` | Для каждого из семи: `enabled`, пороги (10% долга, 90 дней и 10 000 ₽, 60 мес., доля учредителя 25%, перечень кодов ОКВЭД, статусы «не действует») | 30-04 |
| `flags` | Пороги: просрочка 30–89, расхождения 30% и 0,5, накачка (1,6 · 3,5 · 1,3), транзит (0,985 · 9 из 12), один плательщик (2 · 6 мес. · 3 млн), исключённые ОКВЭД | 30-04, 30-02 |

| `scorecard` | Факторы: интервалы, баллы, «нет данных», потолки грейда | 30-07 |

## Версии

| Что | Как |
|---|---|
| Идентификатор | Целое число: `v1`, `v2`. Менять число в существующем файле нельзя, любая правка параметра — новый файл |
| Регистрация | При старте `api` читает файл, проверяет по схеме (невалидный файл — `api` не стартует), приводит к каноническому виду (ключи по алфавиту, без пробелов) и считает SHA-256. Запись есть — используем, нет — добавляем в `policy_versions` |
| `policy_versions` | `version`, `content_hash` (уникален), `content` (полная копия), `effective_from`, плюс `description` и `parent_hash` (на какой версии основана) |
| Какую версию применять | Ту, что активна в `POLICY_FILE` на момент **начала прогона**. Оба вызова `decide()` одного прогона (30-01) используют одну версию |
| Повторный прогон | `NEEDS_INFO → CHECKING` и `MANUAL_REVIEW → CHECKING` применяют текущую версию. Если она сменилась, в таймлайне и карточке написано «правила обновлены» |
| Смена версии | Новый файл + `POLICY_FILE` + перезапуск. Историю даёт git, а содержимое каждой применявшейся версии — таблица |
| Обязательное правило PR | Прогон всех персон (10-02) на новой версии. Если ожидаемый исход изменился, PR обязан изменить таблицу ожидаемых исходов (10-02) явно |

**Ближайшая смена.** Ключевая ставка ЦБ решается 23.10.2026 (30-18 №1): после заседания выпускается `v2` с новой стоимостью денег (ключевая + 1 п.п.), персоны перепрогоняются.

## Снимок решения ссылается на версию

В `decisions` хранятся `policy_version_id`, `engine_version` (хеш коммита пакета `decisioning`), `inputs` и `inputs_hash`. Таблица неизменяема (триггер, 50-06). Решение андеррайтера — новая запись со ссылкой на прежнюю (30-11).

## Воспроизведение решения

| Шаг | Что происходит |
|---|---|
| 1 | Берём `decisions.inputs`: версию заявки, `APP_TODAY`, ссылки на `source_snapshots`. У каждого снимка проверяем `payload_hash` |
| 2 | Берём `policy_versions.content` по `policy_version_id` решения |
| 3 | Вызываем `decide()` (текущий код) в режиме решения |
| 4 | Сравниваем исход, коды причин, все числа (выручка, поток, баллы, грейд, DSCR, ставка, варианты). Расхождения — списком |
| 5 | Результат: «совпало» или «расхождение + поле». Если `engine_version` отличается от текущей, пишем: «ядро менялось после решения» |

Где виден результат: кнопка «Проверить воспроизводимость» в карточке андеррайтера; в CI — «золотые» решения всех персон (хранятся в репозитории) пересчитываются при каждом прогоне, расхождение роняет тест. Старое решение остаётся объяснимым после смены правил, потому что у него своя версия.

## Песочница «а что если» *(Could, Q-070 вариант Б)*

Риск-менеджер меняет параметр (например, DSCR 1,25 → 1,40) и видит эффект на выборке, ничего не сохраняя.

| Элемент | Решение |
|---|---|
| Вход | Список правок «путь параметра → значение» поверх активной версии; выборка: сохранённые решения (персоны) или синтетический портфель с seed (30-06) |
| Что считается | `decide()` на каждой записи с исправленной политикой |
| Результат | Таблица «было → стало»: доли исходов (`APPROVED`, `COUNTER_OFFER`, `MANUAL_REVIEW`, `REJECTED`), распределение грейдов, средняя ставка, сумма ожидаемых потерь; список персон, у которых исход изменился |
| Ограничения | Ничего не пишет в базу, не создаёт версию, не меняет активные правила; доступна ролям андеррайтера и администратора; включается `POLICY_EDIT_ENABLED` |

## Границы

- **Входит:** состав конфига, версии, ссылка решения на версию, воспроизведение, песочница.
- **Не входит:** сами значения (в документах-источниках 10-06, 30-04, 30-07…), формат YAML, редактирование правил через интерфейс (Q-070, вариант В не берём).

## Как проверяем

- Схема: невалидный файл (нет `source`, неизвестный ключ, грейды не покрывают 0–100) → `api` не стартует.
- Сверка с реестром: ключи `key_rate`, `spread`, `lgd_*`, `vat_schedule`, маржа, DSCR совпадают с 30-18.
- Для каждого порога — тест «чуть ниже / ровно / чуть выше».
- Хеш: тот же файл с другим форматированием даёт тот же хеш; правка числа — другой.
- Воспроизведение: решения всех персон пересчитываются побайтно; искусственная правка `inputs` ловится по `payload_hash`.
- Смена версии посреди прогона не смешивает версии.

## Открытые вопросы

**Q-113. Где хранить тексты причин.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Внутри политики | Одна версия — весь результат | Правка опечатки меняет хеш и создаёт «версию правил» без изменения решений |
| Б. Отдельный каталог `texts/ru`, тексты собираются при решении и сохраняются в снимке | Опечатки правятся без новой версии; старые решения не меняются | Два файла для согласованности (тест полноты) |

**Рекомендация: Б.** Q-070 (песочница и правка через API) остаётся в 50-13; здесь рекомендация та же: песочница — Could после сквозного сценария.

## Заметки для реализации

- Читает файл `pipeline` (при старте), ядро получает уже разобранные типы (50-04). Хеш считается от канонической формы, не от байтов файла.
- Сумма в `inputs` должна включать всё, что ядро читает: забытое поле = невоспроизводимое решение. Тест: `decide()` с копией `inputs` из базы даёт тот же результат, а с вынутым полем — падает.
- `engine_version` берётся из сборки образа (хеш коммита), не из часов.
- Веса поиска встречных и сетки — в конфиге, чтобы песочница видела их тоже.
