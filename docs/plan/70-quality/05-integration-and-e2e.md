## Зачем

Юнит-тесты не видят, как ведут себя настоящие Postgres и Redis, гонки и перезапуски. Сквозные тесты доказывают главное для жюри: **персона проходит путь от входа до результата в браузере**. Эти же сценарии — шаги самопроверки жюри (D-064).

## Три слоя

| Слой | Среда | Что видит |
|---|---|---|
| **Интеграционные** (`api/tests/integration/`) | `api` в процессе теста, настоящие Postgres 17 и Redis, моки заменены заглушками | База, блокировки, очередь, пул |
| **Персоны по API** (`api/tests/personas/`) | Весь compose с живыми моками, запросы по HTTP без браузера | Исход и коды причин каждой из 9 персон и 9 технических сценариев |
| **e2e** (`web/e2e/`, Playwright) | Весь compose, настоящий браузер | То, что видит человек |

## Интеграционные тесты

| Область | Проверяем |
|---|---|
| Миграции | Чистая база → `upgrade head` → `downgrade` на шаг → `upgrade`; модели в коде совпадают с миграциями |
| Ограничения БД | Уникальность активной заявки компании (`DUPLICATE_APPLICATION`), внешние ключи, `JSONB`-снимки читаются обратно без потерь |
| Переход статуса под гонкой | Два потока одновременно «отправляют» одну заявку: один успех, другой `409`; версия выросла один раз |
| Outbox | Два доставщика не берут одно сообщение (`SKIP LOCKED`); запись и смена статуса — одна транзакция (откат откатывает обе) |
| Идемпотентность | Таблица `idempotency_keys`: повтор, расхождение тела, «брошенный» ключ через срок |
| Redis | Сессии, лимит частоты, состояние предохранителя, публикация события → открытый SSE-поток получает его; после обрыва докачка по `Last-Event-ID` |
| Celery | Реальный воркер в тесте: `pipeline.run` доходит до решения; сторож возвращает потерянную заявку; воркер «убит» в середине шага (задача вернулась в очередь) |
| Права | Матрица ролей 50-09 по всем ручкам, пара «своя — чужая» компании |
| Документы | Загрузка трёх выписок (хорошая, чужой ИНН, битые суммы) и «PDF» с расширением `.txt`; PDF договора содержит сумму, ставку, номер заявки, ИНН |

Изоляция: контейнеры Postgres и Redis поднимаются один раз на прогон; каждый тест работает в чистой схеме (откат транзакции или `TRUNCATE`, `FLUSHDB` для Redis). Время — только `APP_TODAY`.

## Сброс данных перед сквозным тестом

Правило моков: перед **каждым** прогоном персоны вызывается `POST /api/v1/scenarios/{code}/apply` (раздел 11). Без этого выдачи и запросы в БКИ накапливаются, и следующий прогон видит уже другого клиента.

**Но `apply` чистит только моки.** Заявки, кредиты и согласия живут в базе `api`; единый сброс (`POST /demo/reset`) чистит и их, но делает это для всех сразу. Значит, при втором прогоне Соколовой первая заявка ещё «в работе» и вторая получит `DUPLICATE_APPLICATION`. Нужен способ сбросить **одну** компанию целиком: моки и данные `api`. Выбор — в Q-105.

## e2e по персонам

Общее: e2e входит через интерфейс по ИНН, выбирает пользователя и вводит демо-код с экрана (D-062); `POST /demo/personas/{code}/login` допустим только как хелпер интеграционных тестов при DEMO_MODE и не заменяет e2e входа; андеррайтер — кнопкой «Войти как андеррайтер» (D-010). Стенд: `DEMO_MODE=true`, таймер истечения сроков выключен (20-02). Элементы ищем по роли и подписи, как их видит человек, а не по CSS.

| Тест | Путь | Что проверяем на экране | TS |
|---|---|---|---|
| `sokolova` | Мастер → заявка → `APPROVED` → принять → подписать → `DISBURSED` | Таймлайн идёт **без перезагрузки**; «500 000 ₽ на счёте»; «Мои кредиты»: график 12 платежей | TS-001 |
| `snabkontrakt` | `COUNTER_OFFER` (`DSCR_LOW`) → 3 карточки → «36 мес» → подпись → выдача | «Рекомендуем» одна; блок «как получить то, что просили»; платёж на карточке = в графике | TS-002, 003 |
| `stankoprom` | `MANUAL_REVIEW` → андеррайтер просит договор → Белова загружает → снова ручное → `APPROVED` → Белова «передать руководителю» → Кузнецов подписывает | Бухгалтер не видит «Подписать»; задача клиента видна с «зачем» и сроком | TS-004…006 |
| `garipov` | `NEEDS_INFO` (`REVENUE_UNKNOWN`) → выписка 1С → `APPROVED` → открытие счёта → выдача | Загрузка файла, понятная ошибка на чужой выписке; шаг «открываем счёт» | TS-007, 008 |
| `romashka` | `REJECTED` (`TAX_ARREARS_HIGH`) | Причина простыми словами и «что сделать»; в журнале вызовов нет запроса в БКИ | TS-009 |
| `vektor` | `REJECTED` (`COMPANY_NOT_ACTIVE`) | Отказ на первом шаге | TS-010 |
| `orlov` | `NOT_ELIGIBLE` на вводе ИНН | Нет тупика: объяснение и «как стать ИП»; заявка не создаётся | TS-011 |
| `zarya` | Линия 20 млн → `MANUAL_REVIEW` → `APPROVED` андеррайтером | Продукт «кредитная линия», лимит | TS-012 |
| `quick-start` | `COUNTER_OFFER` «с поручительством» → принять, поручитель сам подписывает согласие → `MANUAL_REVIEW` → `APPROVED` | Поручитель — пользователь кабинета (D-082) | TS-013, 014 |
| Банк | Очередь → карточка → решение; отклонение от рекомендации без причины не проходит | Клиент не видит баллы; андеррайтер видит | TS-030…037 |
| Живые статусы | Рестарт `worker`, затем `redis` посреди проверки | Заявка доходит до итога, вход не слетает | TS-066, 067 |
| Демо-панель | «Уронить БКИ» → заявка на ручное → «починить» → «перепроверить» | Понятные сообщения | TS-060 |

Технические сценарии `t-*` (9 штук) в браузере не гоняем: они идут слоем «персоны по API» и видны в карточке андеррайтера (TS-020…028).

Практика Playwright: Chromium; на падении сохраняем трассу, видео и скриншот; один повтор только в CI; ожидание решения — до 90 с (в интерфейсе обещано «обычно до минуты»); для каждой персоны свой сброс; чаос-тесты идут отдельным последовательным проходом (70-06).

## Прогон коллекции запросов

- Формат **Bruno**, папка `docs/api/collection/` (моки, раздел 11): `mocks/` (по запросу на персону и на каждую ошибку; в каждой папке первым идёт `apply`) и `api/` («Сценарий самопроверки по персонам»).
- В CI: `bru run` с окружением `ci` против поднятого compose; проверки (статус, ключевые поля) лежат в самих запросах. Красный запрос → красный CI (RQ-19).
- В коллекции нет секретов: только локальные ключи моков из `.env.example`.

## Smoke на чистой машине

`scripts/smoke.sh` (50-14): `/health/ready`, вход, заявка `sokolova` до `APPROVED`. Запускается в CI после `docker compose up --wait` и на облачном стенде. Красный smoke — сдавать нельзя.

## Развилки для пользователя

**Q-104. Где берём Postgres и Redis для интеграционных тестов.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Testcontainers (pytest сам поднимает контейнеры) | `pytest` работает на любом ПК одной командой; изоляция | Нужен доступ к Docker; +5–10 с на старт |
| B. Сервисные контейнеры CI / `docker compose up postgres redis` | Тот же стенд, что у e2e; нет доп. библиотеки | Локально надо помнить поднять; легко запустить на «чужой» базе |
| C. SQLite и fakeredis | Мгновенно | Не ловит `SKIP LOCKED`, `JSONB`, блокировки: ровно то, ради чего тесты |

**Рекомендация: A.** Агент не забудет поднять базу, а Codex на другом ПК получит те же условия. Для e2e в любом случае compose.

**Q-105. Как сбрасывать данные одной персоны.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. `POST /demo/reset` перед каждым тестом | Уже есть в 50-07 | Сбрасывает всех, медленно (моки заново), персоны не идут параллельно |
| B. Новая ручка `POST /demo/personas/{code}/reset`: `apply` в `mock-scenarios` + чистка данных этой компании в `api` | Быстро; персоны идут параллельно; то же пригодится жюри | Одна ручка в 50-07 и правило «чистим только эту компанию» |
| C. Каждому тесту своя копия персоны (`POST /demo/scenarios`) | Полная изоляция | Копия ≠ встроенная персона (другие ИНН), жюри так не ходит |

**Рекомендация: B.** Платим одной ручкой в API; взамен e2e идут быстрее и параллельно, а жюри получает «сбросить мою компанию» вместо общего сброса.

## Заметки для реализации

- Параллельность: по персонам можно (разные компании), внутри персоны строго по порядку. Тесты со сбоями моков не параллелим ни с чем.
- `waitForStatus` читает таймлайн и никогда не перезагружает страницу: так проверяется RQ-05.
- Тексты на экране проверяем по словарю 60-06, а не по копии строки в тесте.
- Шаги андеррайтера в e2e идут через минимальный интерфейс банка (D-010), в тестах по API — теми же ручками с ролью `UNDERWRITER`.
