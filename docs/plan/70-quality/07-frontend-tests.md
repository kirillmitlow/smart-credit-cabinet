## Зачем

Жюри оценивает UX (критерий 03): понятно ли, что делать на каждом шаге. Сквозные тесты (70-05) проверяют путь целиком, но медленно и грубо. Компонентные тесты быстро ловят ошибки в логике экранов: ветвление мастера, кнопки по ролям, обновление таймлайна, защиту от двойного клика.

## Инструменты

| Инструмент | Роль |
|---|---|
| Vitest | Запуск тестов, покрытие (V8) |
| Testing Library (React) и user-event | Тест «как пользователь»: ищем по роли и подписи, нажимаем, печатаем |
| MSW | Подмена сервера. Обработчики берутся из OpenAPI (генерирует orval), поэтому ответы всегда по схеме |
| Мок `EventSource` | Управляемый поток событий для таймлайна |
| vitest-axe | Проверка доступности (axe) в каждом экранном тесте |
| eslint-plugin-jsx-a11y | Статическая проверка доступности в линтере |
| Playwright + `@axe-core/playwright` | Контраст и фокус на живом стенде (jsdom цвет не считает) |

Принцип: тесты не знают внутренностей компонентов, только видимый результат. Данные запросов — фабрики, а не копии JSON.

## Что тестируем

| Область | Сценарии | TS |
|---|---|---|
| **Мастер подбора** | Один вопрос на экран; ветвление по ответу на первый вопрос; «Не знаю» не блокирует и даёт подсказку; сумма — число, помощник «сколько закупаете в месяц»; `collateral` показывается, только если сумма выше порога; назад → смена ответа → пересчёт; известное не спрашиваем (отрасль, возраст); результат: один основной и одна альтернатива с «почему подходит», платёжом и сроком решения; ответы попадают в черновик заявки; поле «своими словами» скрыто, если сервис модели недоступен. Таблицу «ответы → продукт» фронт не копирует: её проверяет бэкенд | TS-080…082 |
| **Калькулятор платежа** | Значения приходят из `POST /calculator/payment`; пока ждём — состояние загрузки; сумма и срок вне рамок продукта — понятная подсказка, запрос не уходит; формат: `500 000 ₽`, проценты с запятой; быстрый ввод не шлёт запрос на каждую цифру; сбой сервера — текст из словаря | TS-083 |
| **Заявка (форма)** | Автосохранение черновика с версией; `VERSION_CONFLICT` → понятный баннер и обновление данных; проверка ИНН (10 или 12 цифр, контрольная сумма); без согласий кнопка «Отправить» неактивна; автозаполнение показывает источник каждого поля; сбой реестра → «не подтверждено», поля открыты | TS-053, 057 |
| **Таймлайн** | Шесть клиентских шагов и подшаги проверки соответствуют статусам из 20-02; `NEEDS_INFO` — «Нужна ваша помощь» с «что, зачем, срок»; событие потока двигает шаг **без перезагрузки**; повтор события не дублирует шаг; после обрыва и `resync` состояние совпадает с сервером; `auth_expired` → экран входа; шаги озвучиваются скринридеру (вежливая live-область) | TS-070, 071 |
| **Карточки встречного** | Не больше трёх; «рекомендуем» ровно одна; на карточке сумма, срок, платёж, переплата, ставка, «что нужно от вас», «почему»; выбор шлёт принятие с `Idempotency-Key`, двойной клик даёт один запрос; блок «как получить то, что просили» возвращает заявку в проверку; пустой набор → экран отказа с причиной | TS-002, 003 |
| **Роли в интерфейсе** | Кнопки строятся по `allowedActions` ответа, а не по своей копии стейт-машины; директор видит «Подписать», бухгалтер «Передать руководителю на подпись»; баллы и внутренности только у андеррайтера; клиентская схема их не содержит | TS-005, 037, 040 |
| **Ошибки** | Каждый `code` из схемы показывает текст из словаря 60-06; неизвестный код → общий текст и номер запроса для поддержки; `401` → вход; `429` с `Retry-After` → «повторите через N секунд»; `503` → «сервис временно недоступен» | TS-044 |
| **Мои кредиты** | Итог графика = сумма долга + проценты, строки сходятся с итогом; платёж на карточке равен платежу в графике | TS-001, 090 |
| **Банк** | Очередь обновляется потоком; в карточке рекомендация ядра и причины; «отклониться» без причины не отправляется | TS-030…035 |
| **Демо-панель** | «Уронить БКИ» просит подтверждение и показывает текущий режим; в обычном режиме (`DEMO_MODE=false`) панели нет | TS-060 |
| **Состояния экранов** | Для каждого экрана из 60-03: загрузка, пусто, ошибка, ошибка сети | Все |
| **Тексты** | Для каждого кода причины 30-12 и статуса есть клиентский текст; в клиентских формулировках нет слов «аннуитетный», «обеспечение», «кассовый разрыв», «цель кредитования» (словарь 10-07) | TS-009 |

## Доступность

Десктопная версия (D-063), ориентир — WCAG 2.1 уровня AA для ключевых экранов.

| Что | Как проверяем |
|---|---|
| Нарушения axe | В каждом экранном тесте: ноль нарушений. Экраны: вход, мастер (каждый шаг), калькулятор, форма заявки, таймлайн, решение (все исходы), встречные, подписание, «Мои кредиты», очередь банка |
| Контраст, видимый фокус | Playwright + axe на живом стенде: ключевые экраны в светлой теме |
| Клавиатура | Тесты: весь мастер и подача заявки проходятся клавишами; порядок Tab логичен; при смене шага фокус переходит на заголовок; Escape закрывает окна |
| Подписи и роли | Поля с `label`, кнопки с понятным названием, иконки с текстом для скринридера |
| Динамика | Смена статуса объявляется вежливой live-областью; ошибка поля связана с полем |
| Статический контроль | Правила `jsx-a11y` в ESLint — ошибки, не предупреждения |

Вручную перед сдачей: 10 минут с клавиатурой и масштаб 200% на ключевом пути. Цель — «не отпугнуть» жюри, а не сертификат.

## Скорость и покрытие

- Весь набор компонентных тестов до минуты; тест дольше 2 секунд — повод упростить.
- Порог покрытия — 70% по строкам (70-01), сгенерированный клиент не считается.
- Снимочные тесты («snapshot») для вёрстки не используем: они ломаются от любой правки и ничего не доказывают. Скриншоты нужны только Playwright и только для материалов сдачи.

## Решённые развилки

**Q-107. Насколько строго держим доступность в CI.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Блокируем merge при нарушениях axe уровня «критично» и «серьёзно»; остальное в отчёт | Реальная защита без лишнего шума | Иногда придётся править мелочи ради зелёного CI |
| B. Блокируем любые нарушения | Максимум | Шум от сторонних компонентов библиотеки, потери времени |
| C. Только отчёт | Не мешает | Через неделю никто не смотрит |

**Рекомендация: A.** Несколько правил можно отключить точечно с комментарием «почему» (например, сторонний компонент даты).

## Заметки для реализации

- Фабрики данных и обработчики MSW генерируются из схемы: перегенерация клиента (70-04) обновляет и их.
- Если библиотека компонентов (60-02) уже даёт доступные компоненты, тесты проверяют нашу сборку из них, а не её внутренности.
- Тексты ошибок и статусов не вшиваются в тесты: берём из словаря `texts/` (60-06).
