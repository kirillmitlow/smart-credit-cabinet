## Зачем

CI — единственный «ревьюер», которому доверяют оба агента: Claude Code и Codex сидят на разных ПК. Правило: **что не зелёное в CI, то не влито**. CI запускает те же команды, что и `make check` и `make test` (50-03): расхождение «у меня работает» исключено.

## Когда что запускается

| Триггер | Набор | Зачем |
|---|---|---|
| Pull request | **Быстрый** (до ~15 мин по часам) | Закрыть merge только по главному |
| Push в `main` | **Полный** | Все слои, включая синтетику 10 000 и хаос |
| Ночью (расписание) | Полный + глубокие property + нагрузка | Редкие ошибки, дрейф метрик |
| Тег `submission` (и вручную) | Полный + публикация образов | Только в момент сдачи (D-083) |

Изменения только в `docs/plan/**` запускают одну лёгкую задачу `docs` (ссылки, шапки, mermaid), тяжёлое пропускается. Чтобы пропущенные задачи не блокировали merge, обязательной проверкой делается **одна итоговая задача `ci-ok`**, которая зелёная, когда зелены все нужные.

## Публикация образов (D-081, D-083)

- Задача `release` запускается **только** по тегу `submission` и вручную подтверждённым запуском. До этого образы никуда не публикуются; в обычных запусках `build` только собирает.
- Перед публикацией: проверка, что в образы не попали `docs/` и PDF кейса; `trivy image` зелёный; образы помечены хешем коммита, базовые — по точной версии.
- Права на запись пакетов выдаются только этой задаче. Секретов, кроме встроенного токена, нет.
- Пакеты публичные, а значит, код в образах виден всем: пользователь принял (D-081). Перед тегом проверяется, как `compose` выбирает между `image` и `build`.

## Время и кэш

Ориентиры (допущение, замерить на первых запусках):

| Набор | Ожидаем | Предел, при превышении оптимизируем |
|---|---|---|
| Быстрый, часы | 12–15 мин | 20 мин |
| Полный | 25–30 мин | 40 мин |
| Ночной с нагрузкой | 45–60 мин | 90 мин |

Что кэшируем: пакеты `uv` (ключ — хеш `uv.lock`), хранилище `pnpm` (ключ — lock-файл), слои Docker через кэш Actions, браузеры Playwright (ключ — версия), кэши `ruff` и `mypy`, база уязвимостей `trivy`, каталог примеров Hypothesis (повторяет ранее найденные падения). Задачи идут параллельно; новый запуск того же PR отменяет предыдущий.

## Что блокирует merge

- Красный `ci-ok` в PR. В него входят: `lint-py`, `lint-web`, `arch`, `docs`, `unit` (с порогами), `property`, `openapi`, `web-unit`, `integration`, `synthetic` (малый), `build`, `e2e` (сокращённый), `security`, `notices`.
- Merge в `main` — только с согласия пользователя (D-00E), поэтому зелёный CI необходим, но недостаточен.
- Красный `main` чинится первым делом и записывается в `08-handoff.md`.
- Перед тегом `submission` зелёными должны быть **все** задачи полного набора, включая `resilience` и `load`; это пункт чек-листа 80-05.

## Бейджи и отчёты

- В README: статус CI на `main` и статус ночного прогона (встроенные бейджи Actions; репозиторий закрытый, но проверяющие имеют доступ).
- Покрытие, число тестов, метрики синтетики — не бейджами внешних сервисов (RQ-51: без сторонних подписок), а таблицей «Качество» в README, которую заполняет скрипт из артефактов.
- Артефакты на 14 дней: покрытие, отчёт JUnit, отчёт и трассы Playwright, `synthetic-report`, выгрузка OpenAPI, отчёты `trivy` и аудитов, отчёт нагрузки, логи контейнеров упавшего запуска.
- Сводка каждого запуска (`$GITHUB_STEP_SUMMARY`) содержит ключевые числа.

## Развилки для пользователя

**Q-108. Что гоняем в каждом PR, а что только на `main`.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Быстрый набор в PR (без полного e2e, хаоса, нагрузки, полной синтетики), полный на `main`, ночью и перед тегом | PR зелёный за ~15 минут; расход минут Actions умеренный | Редкая проблема всплывает после слияния; нужна дисциплина «красный `main` чиним сразу» |
| B. Всё в каждом PR | Максимальная защита | PR по 30–40 минут; на закрытом репозитории возможен упор в бесплатный лимит минут Actions (лимит и ограничения защиты веток зависят от тарифа, проверить) |
| C. Только линт и unit, остальное руками | Дёшево | Теряем смысл CI для критерия «Enterprise» |

**Рекомендация: A.** Платим отложенным обнаружением. Если тариф не позволяет обязательные проверки на закрытом репозитории, «блокировка» становится договорённостью: агент не просит merge при красном CI.

## Заметки для реализации

- Первый коммит кода — каркас с зелёным `ci-ok` на одном тесте (50-03); задачи подключаются по мере появления кода.
- Версии действий Actions фиксируем точными, а не `latest`; пакеты по lock-файлам (RQ-13).
- Фронт использует `pnpm` (Q-049 А), поэтому в 50-09 «`npm audit`» читать как `pnpm audit`.
- Все долгие инструменты запускаются через `make`: `make check`, `make test`, `make openapi` (50-03). CI не знает флагов, которых нет в Makefile.
- Секретов в обычных запусках нет; запуски из форков не предполагаются.
