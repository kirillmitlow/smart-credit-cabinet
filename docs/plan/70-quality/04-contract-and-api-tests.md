## Зачем

В системе семь «договоров»: API для фронта, четыре мока, сервис сценариев и клиент TypeScript. Если они молча разойдутся, жюри увидит ошибку на демо. Контрактные тесты держат их согласованными. Схема OpenAPI строится из кода (Q-059 A), поэтому главная защита от расхождения — **сверка выгрузки с закоммиченным файлом**.

## Что проверяем

| # | Проверка | Как | Что ловит |
|---|---|---|---|
| 1 | Выгруженный OpenAPI = закоммиченный | `make openapi` в CI и сравнение с `docs/api/*.openapi.yaml` (`api`, 4 мока, `mock-scenarios`) | Изменили ручку и забыли обновить документ (RQ-18) |
| 2 | Нет критичных изменений относительно `main` | `oasdiff` | Удалили поле, сменили смысл (правило «поля в `v1` не удаляем») |
| 3 | Качество схемы | Spectral: у всех ручек `operationId`, описаны ошибки, имена `camelCase`, есть схемы безопасности (`ApiKeyAuth`, `AdminKeyAuth` у моков) | Нечитаемая схема для жюри |
| 4 | TS-клиент совпадает со схемой | `orval` перегенерирует клиент, различия с закоммиченным → красный; затем `tsc --noEmit` | Фронт и бэк разъехались в полях |

## Фаззинг API (Schemathesis)

Schemathesis читает OpenAPI и сам придумывает запросы: граничные числа, пустые строки, лишние поля.

| Параметр | Значение |
|---|---|
| Что считается ошибкой | Любой `5xx`, кроме `503` при включённом сбое; ответ не по схеме; неописанный код ответа; неверный `Content-Type` |
| Вход | Cookie сессии демо-персоны (директор) и отдельный прогон под андеррайтером |
| Исключения | `/demo/reset` и `/demo/chaos` (ломают стенд), `GET /events` (поток), загрузка файлов (проверяется отдельно) |
| Размер | В PR — 50 примеров на ручку; ночью — 500 |
| Где | Против поднятого стенда с изолированной базой |
| Моки | Ночью те же проверки против `mock-*`: на странный ввод мок обязан отвечать `422`, а не `500` |
| Связанные сценарии (stateful) | Could: цепочка «создать → отправить → отозвать» по ссылкам схемы |

Найденное фаззингом чинится кодом или явно описывается в схеме. Исключение из проверки допустимо только с комментарием «почему».

## Контрактные тесты адаптеров

Адаптеры (`api/app/integrations/<система>/`) не импортируют код моков (разные системы). Договор — только `docs/api/mock-*.openapi.yaml`. Тесты двух видов:

| Вид | Как | Когда |
|---|---|---|
| **Образцы против схемы** (быстро, без сети) | Образцы ответов, на которые рассчитывает адаптер (заглушки respx), проверяются по схеме мока. Мок изменил формат → тест красный раньше, чем адаптер | Каждый PR |
| **Против живых моков** (`api/tests/contract/`) | Адаптер идёт в настоящие моки в compose. Данные — встроенные сценарии | Задача `e2e` и ночью |

Что проверяется для каждого адаптера:

| Система | Проверки |
|---|---|
| registry | Карточка каждой персоны ложится во внутреннюю модель; `404` у `orlov`; недействующая компания у `vektor`; роли человека; банкротства: пустой список и дело учредителя у `t-bankrupt` |
| tax | Профиль, отчётность (в том числе `404 STATEMENTS_NOT_FOUND` у Гарипова), МСП, НПД, блокировки; контракты ЕИС только у СнабКонтракта |
| credit-bureau | Отчёт по компании, директору и поручителю; **5 причин `403` по согласию** превращаются в понятные внутренние ошибки; повтор с тем же `Idempotency-Key` не плодит запросов; арифметика примера 6.1 воспроизводится |
| bank-core | Клиент или нет, обороты, выдача: `409 ALREADY_DISBURSED`, `409 ACCOUNT_NOT_OWNED`; повтор с ключом возвращает сохранённый ответ |
| mock-scenarios | `apply`, `reset` (после него chaos в `OK`), `preview` |

Общие для всех адаптеров проверки поведения (моки подставляются режимами сбоев, 70-06):

| Поведение | Ожидаем |
|---|---|
| Таймаут (БКИ 5 с, остальные 1–2 с) | Ошибка за указанное время, повтор по таблице 50-08 |
| `503`, обрыв | Повторяем `GET` и `POST` с ключом; `POST` без ключа **не** повторяем |
| `429` | Уважаем `Retry-After` |
| Предохранитель | 5 ошибок за 30 с → открыт на 30 с → полуоткрыт → закрыт; состояние в Redis |
| Неверный формат ответа | `SCHEMA_ERROR`, как недоступность источника |
| Заголовки | Сквозной `X-Request-Id`, свой `Idempotency-Key` по заявке и субъекту |

## Проверки самого `api` по контракту

Тесты, которые ходят в `api` напрямую (ASGI, без браузера) и не требуют моков:

- повторы и расхождение тела при `Idempotency-Key`; параллельный повтор → `409 IDEMPOTENCY_IN_PROGRESS` с `Retry-After`;
- пара «своя компания — чужая компания → `404`» на каждый ресурс с `companyId`;
- недопустимый переход → `409 INVALID_TRANSITION`;
- `DEMO_MODE=false` → `403 DEMO_MODE_DISABLED` на всех `/demo/*`;
- `X-Request-Id` возвращается в ответе и попадает в журнал.

## Развилки для пользователя

**Q-103. Чем фаззить API.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Schemathesis | Читает нашу схему, находит `500` сам, умеет вести проверки по схеме ответов, бесплатный, на Python | Нужна настройка входа и списка исключений; шумит, пока схема неточная |
| B. Только свои параметризованные тесты на странные входы | Полный контроль, нет новых инструментов | Мы увидим только то, о чём подумали заранее |
| C. Фаззер уровня HTTP (общие инструменты) | Ловит низкоуровневое | Не знает наших схем, много пустого шума |

**Рекомендация: A**, плюс свои тесты для критичных ручек (подача, подпись). Платим временем на настройку (около часа) и разбором первых находок.

## Заметки для реализации

- Коллекция запросов — формат Bruno (так записано в моках, 11), прогон в CI описан в [70-05](05-integration-and-e2e.md). В матрице 10-01 RQ-19 указывает на 70-04; фактически прогон описан в 70-05, ссылку поправить.
- Схему не править руками: правится код, затем `make openapi`. Закоммитить выгрузку и клиент вместе с кодом одним коммитом (50-03).
- `operationId` в формате `<ресурс><Действие>` проверяет Spectral, иначе orval выдаёт нечитаемые имена.
- Тесты обращений к мокам используют **встроенные сценарии**; свои данные создаются только через админ-API после `apply` (см. 70-05).
