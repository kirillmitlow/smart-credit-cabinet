## Зачем

Критерий «Enterprise» оценивает не то, что система работает, пока всё хорошо, а что **она не врёт и не ломается, когда плохо**. Моки умеют сбои (`SLOW`, `ERROR`, `DOWN`, `TIMEOUT`, `LOST_RESPONSE`), и мы проверяем автотестами то, что показываем жюри кнопкой «уронить БКИ».

## Хаос-сценарии

Каждый сценарий — автотест (`api/tests/resilience/`, метка `chaos`) на живом compose. Сбой включается через `PUT /admin/chaos` мока (либо через `/demo/chaos`), в конце **всегда** `scenarios/reset`: он возвращает `OK` у всех четырёх.

| # | Сбой | Что делаем | Ожидаемо | TS |
|---|---|---|---|---|
| H-01 | БКИ `DOWN` | Подаём заявку `sokolova` | Заявка не падает: `MANUAL_REVIEW` с флагом `SOURCE_UNAVAILABLE`; в таймлайне понятно, что БКИ недоступно; предохранитель открылся. Починили → андеррайтер «перепроверить» → `CHECKING` → `APPROVED` | TS-060 |
| H-02 | `mock-registry` или `mock-tax` `DOWN` | Автозаполнение, затем конвейер | Автозаполнение: поля вручную с пометкой «не подтверждено». Конвейер: `MANUAL_REVIEW`, `SOURCE_UNAVAILABLE` | TS-061 |
| H-03 | БКИ `ERROR`, 50% | Подаём заявку | Повторы сработали; итог тот же, что без сбоя; платных запросов не больше одного на заявку и субъекта | TS-060 |
| H-04 | БКИ `SLOW` (дольше таймаута 5 с) | Подаём заявку | Таймаут адаптера, затем `MANUAL_REVIEW`; в это время `api` отвечает на другие запросы (воркер не заблокировал сервис) | TS-064 |
| H-05 | `TIMEOUT` (подвис на 60 с) | То же | Клиент рвёт вызов по своему таймауту, мягкий лимит задачи не нарушен | TS-064 |
| H-06 | **`LOST_RESPONSE` на выдаче**, 100% | Доводим заявку до `SIGNED` | Outbox повторяет с тем же ключом; **в АБС ровно один кредит**, остаток равен сумме, заявка `DISBURSED`; клиент видел «выдача в обработке» | TS-062 |
| H-07 | `LOST_RESPONSE` на запросе в БКИ | Подаём заявку | Один платный запрос: `inquiries30d` вырос на 1, не на 2 | TS-063 |
| H-08 | АБС `DOWN` при выдаче | После подписи | `DISBURSING` держится; отозвать нельзя; после починки `DISBURSED` без дубля | TS-065 |
| H-09 | БКИ `DOWN` на `submissions` | Выдача проходит | Заявку не блокирует; сообщение ждёт в outbox и уходит после починки; по превышению срока — `FAILED` (срок сжимаем конфигом), видно в демо-панели | TS-065 |
| H-10 | Убили воркер в середине шага | `docker kill worker` на шаге БКИ | Задача вернулась в очередь (`acks_late`); итог тот же; БКИ не задвоен | TS-066 |
| H-11 | Перезапуск `redis` | Во время проверки | Вход не слетает (AOF), SSE переподключается с `Last-Event-ID`, события не потеряны; очередь восстановлена, сторож подбирает застрявшее | TS-067 |
| H-12 | Перезапуск `postgres` | Во время запросов | Ответы `503` в формате `problem+json`; после возврата работает; полусостояний нет | TS-066 |
| H-13 | Двойная отправка | Два одновременных `submit` | Один успех, один `409`; одна задача конвейера | TS-051 |
| H-14 | Разовый сбой `X-Mock-Scenario` | Заголовок на одном запросе | Ломается только он; следующий проходит | TS-064 |

Правила запуска: чаос-тесты идут **по одному** и отдельной задачей CI (режим мока глобален); не параллелятся с e2e; финализатор сбрасывает сбои, даже если тест упал.

## Нагрузочный тест

**Цель:** не рекорд производительности, а доказательство из [50-15](../50-architecture/15-reliability-and-scaling.md): под параллелизмом на нескольких экземплярах система остаётся **корректной**, а время и память укладываются в бюджет. Числа скорости не обещаем.

| Параметр | Значение |
|---|---|
| Стенд | `docker compose up --scale api=2 --scale worker=3`, проверка `ready` каждого |
| Данные | 50 компаний, созданных через `POST /demo/scenarios` пресетами (персон только 9, на компанию одна заявка в работе) |
| Сценарий | 50 виртуальных клиентов: вход → подача → ожидание итога → чтение таймлайна; параллельно 2 андеррайтера читают очередь |
| Нарастание | 0 → 50 за минуту, держим 3 минуты |
| Сравнение | Эталонные итоги берутся от последовательного прогона тех же 50 компаний |

### Что измеряем

| Метрика | Критерий | Тип |
|---|---|---|
| Итоговый статус каждой заявки | Совпадает с эталоном | **Корректность, блокирует** |
| Выдачи в АБС | Ровно один кредит на выданную заявку | Корректность, блокирует |
| Запросы в БКИ | Не больше одного на заявку и субъекта | Корректность, блокирует |
| Аудит | Версии заявки без пропусков, каждому переходу — одно событие | Корректность, блокирует |
| Ошибки `5xx` | 0 (кроме осознанных `503` в хаосе) | Блокирует |
| Время до решения | p50 и p95 фиксируем; ориентир (допущение): p95 до 30 с | Информация, порог мягкий |
| Ответ чтения (`GET` заявки, таймлайн) | p95 до 300 мс (допущение) | Информация |
| Память | Весь стенд ≤ 4 ГБ по `docker stats` (D-066) | Блокирует |
| Подключения к БД | Меньше `max_connections` | Блокирует |
| Очередь | Опустела за N минут после остановки нагрузки | Блокирует |

Кроме того, проверяем, что запросы действительно распределяются между двумя `api` (nginx переразрешает адрес, 50-15): для этого предлагаем, чтобы каждый экземпляр отдавал в заголовке свой идентификатор (в 50-07 его пока нет).

## Развилки для пользователя

**Q-106. Чем создаём нагрузку.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Locust | Сценарии на Python, как весь бэкенд; можно переиспользовать клиентский код тестов; готовый HTML-отчёт; бесплатен | Тяжелее k6 по памяти на одном ПК; метрики менее «модные» |
| B. k6 | Лёгкий, красивые пороги прямо в сценарии | Сценарии на JavaScript — ещё один язык и отдельный бинарь; ходить по сценариям персон придётся переписывать |
| C. Свой скрипт на asyncio и httpx | Ноль зависимостей; ровно наша проверка корректности | Ни отчёта, ни профилей нарастания, всё пишем сами |

**Рекомендация: A.** Корректность проверяется дополнительным скриптом после нагрузки (эталон, АБС, БКИ, аудит), и Python для обоих ближе. Платим памятью инструмента (запускается на раннере CI, не у жюри).

## Заметки для реализации

- Для перезапусков и `kill` фикстуре нужен доступ к Docker (`docker compose` из теста); поэтому слой работает только на хосте с Docker, не в юнит-прогоне.
- Все строки H-01…H-14 дублируются как строки сценария самопроверки жюри (80-07) и кнопки демо-панели (60-05): жюри может повторить руками.
- Предохранитель держит состояние в Redis: после `H-11` проверить, что он не «залип» открытым.
- Для p95 и памяти не хватит одного прогона: фиксируем минимум три и пишем худший.
