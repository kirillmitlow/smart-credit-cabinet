## Цель

Цель не рекорд скорости, а доказательство, что под параллелизмом на двух `api` и трёх воркерах результат корректен, а память укладывается в бюджет.

## Входит / не входит

- **Входит:**
  - Сценарий: 50 виртуальных клиентов (вход, подача, ожидание итога, чтение таймлайна), 2 андеррайтера читают очередь; нарастание 0 → 50 за минуту, 3 минуты удержания; компании создаются пресетами через `POST /demo/scenarios`
  - Проверки корректности: итог каждой заявки совпадает с эталоном последовательного прогона; ровно один кредит на выданную заявку; не больше одного запроса в БКИ на заявку и субъекта; аудит без пропусков; нет `5xx`; память ≤ 4 ГБ; очередь опустела
  - Информационные метрики: p50/p95 времени до решения, p95 чтения; отчёт HTML как артефакт
  - Запуск `docker compose up --scale api=2 --scale worker=3`; проверка, что запросы распределяются между экземплярами
  - Раздел для README «Надёжность и масштабирование»: что делали и что не обещаем
- **Не входит:**
  - Запуск по расписанию ([T-513](T-513-ci-nightly-full.md))

- [ ] Прогон завершается с отчётом, корректность проверена программно (не глазами)

- [ ] Память и подключения к БД записаны в сводку
- [ ] Команда запуска вынесена в `make load` и описана одной строкой в README
- [ ] Тесты написаны и зелёные
- [ ] Документация и OpenAPI обновлены, если менялся контракт
