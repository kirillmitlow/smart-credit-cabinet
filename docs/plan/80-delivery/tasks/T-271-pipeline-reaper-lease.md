## Цель

Заявка не теряется и не зависает: сторож раз в 30 секунд находит запуски без живой задачи и ставит их заново, а после пяти неудач переводит заявку на ручное рассмотрение с флагом `PIPELINE_ERROR`.

## Входит / не входит

- **Входит:** `pipeline.reaper`: заявки `SUBMITTED/CHECKING` без живой аренды → повторная постановка; продолжение с последнего сохранённого шага; ограничение 5 перезапусков одного запуска, затем решение `MANUAL_REVIEW` без признаков (ядро не вызывается) и событие для андеррайтера; корректная работа аренды при убийстве воркера и при потере очереди Redis.
- **Не входит:** разбор причины PIPELINE_ERROR в карточке банка ([T-361](T-361-backoffice-card.md)).

## Критерии приёмки

- [ ] Убить воркер посреди шага БКИ → заявка доезжает до решения, платный отчёт один (интеграционный тест)
- [ ] Очистить Redis после отправки → сторож возвращает задачу
- [ ] Заявка с принудительной ошибкой 5 раз уходит в `MANUAL_REVIEW` с `PIPELINE_ERROR`, воркер жив
- [ ] Сторож не запускает запуск, пока аренда другого процесса жива
- [ ] Тесты написаны и зелёные (`make check`)
- [ ] Документация и OpenAPI обновлены, если менялся контракт
- [ ] Запись в журнале

## Тесты

integration/chaos: kill worker, flush Redis, принудительная ошибка; property: любой порядок сбоев не даёт двух решений на запуск.

## Заметки для реализации

- «Зависшим» считается запуск по системному времени (`locked_until`), а не по `APP_TODAY` ([50-05](../../50-architecture/05-async-processing.md)).
- Подходит для передачи в GPT-6 Astra: тонкая конкурентность.
