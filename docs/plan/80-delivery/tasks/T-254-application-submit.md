## Цель

Клиент отправляет заявку: проверяются обязательные поля и согласия, создаётся неизменяемая версия, статус `SUBMITTED`, после коммита ставится задача `pipeline.run`.

## Входит / не входит

- **Входит:** проверки: обязательные поля, все обязательные согласия подписаны, нет другой заявки компании в работе (`DUPLICATE_APPLICATION`, уникальный индекс на уровне БД); `application_versions(reason=SUBMIT)` с `data_hash`, событие `TRANSITION`, ответ сразу (`200` со статусом), постановка `pipeline.run` по имени после коммита (R10); запись в outbox `APPLICATION_REGISTERED` (если [T-278](T-278-outbox-relay.md) готов; иначе заглушка-хук); защита от двойной отправки: запрет `SUBMITTED → SUBMITTED` и `Idempotency-Key`.
- **Не входит:** сам конвейер ([T-270](T-270-pipeline-skeleton.md)); отзыв ([T-256](T-256-application-withdraw.md)).

## Критерии приёмки

- [ ] Двойное нажатие «Отправить» создаёт одну версию и один запуск (тест с повтором и гонкой)
- [ ] Без подписанных согласий → `422 CONSENT_REQUIRED`; при дубле → `409 DUPLICATE_APPLICATION`, черновик остаётся
- [ ] Заявку, у которой задача потерялась, подхватывает сторож ([T-271](T-271-pipeline-reaper-lease.md)); до его появления — тест вручную вызванной задачей
- [ ] Бухгалтер может отправить, если согласия подписаны уполномоченными ([10-03](../../10-product/03-users-and-roles.md), сноска 1)
- [ ] Тесты написаны и зелёные (`make check`)
- [ ] Документация и OpenAPI обновлены, если менялся контракт
- [ ] Запись в журнале
