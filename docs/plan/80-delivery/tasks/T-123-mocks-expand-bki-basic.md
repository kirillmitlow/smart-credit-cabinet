## Цель

Из коротких параметров (`historyYears`, `activeLoans`, `closedLoans`, `monthlyPaymentsRub`) строятся реальные обязательства с графиком платежей, остатком и УИд. Три разных субъекта БКИ: компания, директор, владелец.

## Входит / не входит

- **Входит:**
  - Субъекты `bki.company`, `bki.director`, `bki.owner` (директор = владелец → один субъект; у ИП компания и владелец — один человек; для АО владельца нет)
  - График кредита: дата открытия (по умолчанию `сегодня − min(срок/2, 18)` мес), день платежа, аннуитет по сумме, сроку и ставке (21% по умолчанию), округление платежа до 100 ₽ и остатка до 1000 ₽; закрытые в срок кредиты, `BULLET`
  - Линия, овердрафт, карта: лимит, использованная часть, платёж 5%
  - УИд в формате UUID + контрольный символ; `ourBank: true` — один УИд в БКИ и в bank-core
  - `historyYears: 0` — субъекта в БКИ нет (`NOT_FOUND`); история компании не старше самой компании
- **Не входит:**
  - Просрочки, запросы, отказы, реструктуризации ([T-124](T-124-mocks-expand-bki-advanced.md))

## Тесты

Unit-тесты графика на таблице примеров, property: остаток убывает монотонно, платёж не превышает сумму; тесты слияния субъектов.

## Заметки для реализации

- Не путать: сумма платежей по активным кредитам идёт в ядро как нагрузка; ошибка здесь сдвигает DSCR всех персон.
- Формулу аннуитета сверить с 30-16 (математика кредита) — ядро будет считать так же.


### Реализовано B, 21.10.2026

Чистый `bki_expand.expand_bki` принимает **разрешённый пресетами** `ScenarioSpec`,
`expanded.identity`, `code`, `today`; необязательный `CreditDefaults` задаёт ставку
(21%) и платёж по лимитам (5%). Генератор пока не подключён к preview: до T-124
он явно отклоняет ненулевые параметры просрочек/запросов/отказов/реструктуризаций.
Контракт API не менялся.

Результат: `bki[] = {inn, body}` — готовые тела админ-PUT БКИ;
`bankLoans[] = {inn, body: {loans: [...]}}` — заготовки для объединения с
`bankCore.customer/accounts` в T-125. Для `historyYears: 0` субъекта нет.
Одинаковые ИНН объединены, противоречащие поля отклоняются `ValueError` (в API
интегратор переводит в `422`). `MICROLOAN`/`CONSUMER_LOAN` нормализуются в
`LOAN`, поскольку контракт БКИ не выделяет эти виды.

Временный `credit_math` реализует формулы 30-16 до появления ядра T-280:
для нашего банка — график с округлением до 1 ₽ и переносом выходных;
для чужого — точная формула остатка, округление платежа до 100 ₽ и остатка до
1000 ₽. Платёж подбирает ставку, если ставка не дана; несовместимая пара
отклоняется. УИд: синтетический детерминированный UUID v1 и контроль по
[758-П, приложение 2, п.5](https://www.cbr.ru/queries/xsltblock/file/117713/0/2286-2287).

**Проверено:** 37 unit/property-тестов (`HYPOTHESIS_PROFILE=ci`, 200 примеров),
mypy всех 85 файлов моков. Векторы: 47 280 ₽ / остаток 264 833 ₽ после 6 платежей
(500 тыс., 12 мес., 24%); платежи 744 910 ₽ и 295 274 ₽ (30-16).
Чистый остаток после 28 оплаченных платежей для примера 3 млн / 36 / 21% =
837 тыс. ₽; полный контроль 452 тыс. / 94 дня остаётся T-124.

**Для интегратора:** `ourBank` допустим для компании/ИП — клиента банка и только
`LOAN`, `CREDIT_LINE`, `OVERDRAFT`, которые умеет существующий bank-core.
Его текущий `outstandingRub` равен исходной сумме (погашения не моделируются,
7.5), поэтому T-123 обеспечивает совпадение УИд и условий, а точный остаток
хранит в БКИ. T-126 должен учитывать это документированное ограничение моков.
Формулы из `credit_math` впоследствии должны использовать общий источник ядра,
а не расходящиеся копии. Журнал, handoff и PR обновляет основной агент.
