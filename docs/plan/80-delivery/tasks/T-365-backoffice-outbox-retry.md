## Цель

Сообщения outbox со статусом `FAILED` видны и повторяются кнопкой (карточка и демо-панель).

## Входит / не входит

- **Входит:** `GET` списка застрявших, `POST /backoffice/outbox/{id}/retry`; запись в аудит.
- **Не входит:** автоповторы (в [T-278](T-278-outbox-relay.md)).

## Реализация B, 23.10

GET /backoffice/outbox: FAILED, фильтр applicationId, limit/cursor. API и интерфейс карточки/очереди показывают систему, число попыток, время, причину; у истёкшего окна24ч или отсутствующей заявки повтор запрещён. POST /backoffice/outbox/{id}/retry требует Idempotency-Key и пустое тело, вызывает public shared.outbox.retry_dead, не меняет исходный ключ получателя/created_at/payload. Ответ PENDING означает постановку на повтор, не доставку.

Изменение, OUTBOX_RETRY-аудит и запись HTTP-ответа — одна транзакция. Очередь outbox.relay ставится после commit. Небольшой shared.idempotency.run_once пишет только свою существующую таблицу, advisory xact lock даёт IN_PROGRESS без ожидания, хранится только2xx на24ч. Это не глобальный middleware остальных ручек. Ключ привязан к пользователю/пути/заявке, поэтому выборочный сброс удаляет его штатным механизмом. HTTP OperationFence держит замок компании, найденной через outbox.aggregate_id; посторонний/удалённый aggregate не отправляется.

11 интеграционных проверок: доставка с тем же ключом, метрика1→0, аудит один раз; повтор HTTP и одновременные нажатия; откат при сбое аудита; потеря ответа после commit/сбоя толчка без второго эффекта; точная граница24ч; права, запросы и сброс. Общие проверки зелёные, 424 web; 36 целевых банковских web, включая4 для доставки. После сетевого сбоя интерфейс повторяет тот же ключ; успех означает «поставлено на повтор». Живой TS-031 с блоком доставки прошёл, axe без critical/serious. Общая демо-панель позже ссылается на банк для повтора, доступ остаётся только банковским.
