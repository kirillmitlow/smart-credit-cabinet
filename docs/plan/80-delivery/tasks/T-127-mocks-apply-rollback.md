## Цель

`apply` раскладывает развёрнутые данные по мокам через их админ-API и откатывает всё при сбое одного. Половинчатых компаний не бывает.

## Входит / не входит

- **Входит:**
  - `split.py`: развёрнутые данные → четыре куска в терминах `PUT /admin/subjects/{inn}` каждого мока
  - `apply.py`: последовательная запись в registry, tax, bki, bank-core с заголовком `X-Scenario-Code`; журнал `scenario_applications` (система, действие, HTTP-статус, ошибка)
  - Откат: при сбое любого мока `DELETE /admin/scenarios/{code}` у уже записанных; сценарий получает `FAILED`, ответ `502 APPLY_FAILED` с названием системы
  - `POST /scenarios` создаёт и применяет (ответ `201` с `applied` по каждому моку: `OK`/`SKIPPED`/`FAILED`); `POST /scenarios/{code}/apply` стирает всё по компании, включая `RUNTIME`-записи, и создаёт заново
  - Статусы `PENDING`, `APPLIED`, `FAILED`
- **Не входит:**
  - Стартовое наполнение ([T-128](T-128-mocks-startup-fill.md)) и досинхронизация ([T-129](T-129-mocks-resync-reset.md))

## Уточнения реализации, 22.10

- Последовательные PUT и журнал; перед HTTP намерение фиксируется в БД.
  При потере ответа очищается также не ответившая система: она могла сохранить запись.
- Общая блокировка Postgres на закреплённом соединении защищает создание, PATCH,
  apply, удаление и фоновый откат между коммитами. Ключ идемпотентности захватывается
  раньше блокировки; конкурент с тем же ключом получает IDEMPOTENCY_IN_PROGRESS.
- Прерванный PENDING и незавершённый FAILED очищаются по журналу в фоне каждые 2 с;
  активную операцию фон пропускает. Данные удаляются после возвращения мока, даже
  если процесс сценариев перезапущен. Полный sync/reset всех персон — T-129.
- DELETE сценария сохраняет намерение до очистки: FAILED + needs_reapply=false.
  Только после удаления во всех системах исчезает строка custom-сценария.
  T-129 должен учитывать это сочетание, а не заново применять удаляемый сценарий.
- Сброс удаляет сохранённые ответы выдач/отчётов/сведений БКИ, относящиеся к стёртым
  ресурсам. Ключи остальных компаний сохраняются.
- GET возвращает applications: system, action, httpStatus, error, at и id записи.
  Новый POST apply и снимок OpenAPI требуют отдельного согласия до слияния.
- Найдено противоречие примера bankCore=SKIPPED у любого не-клиента: T-125 хранит
  для него ЗСК, в том числе GREEN. Предложено считать OK при сохранении комплаенса,
  SKIPPED — только когда совсем нет данных. Клиент/счёт при этом не создаётся.
  Вопрос Q-145 должен быть подтверждён вместе с контрактом PR.
- Для T-128: создавать и применять стартовые сценарии под locked_session;
  не коммитить отдельный PENDING до начала apply, иначе фон сочтёт его прерванным.
