## Цель

Повтор запроса не выдаёт деньги дважды и не оставляет двойной след в БКИ. Один общий механизм для `POST disbursements`, `POST submissions`, `POST customers/{inn}/accounts`, `POST credit-reports` и `POST /scenarios`.

## Входит / не входит

- **Входит:**
  - Таблица `idempotency_keys` в каждой базе (ключ, эндпоинт, хеш тела, состояние `IN_PROGRESS`/`DONE`, ответ, срок)
  - Запись ключа **до** обработчика в состоянии «в работе»; параллельный повтор получает `409 IDEMPOTENCY_IN_PROGRESS` с `Retry-After: 1`; после готовности — тот же ответ и заголовок `Idempotent-Replayed: true`
  - Другое тело при том же ключе — `409 IDEMPOTENCY_KEY_REUSED`; сохраняются только ответы 2xx, после ошибки ключ освобождается
  - «Брошенный» ключ (в работе дольше 60 с) выполняется заново; срок жизни 24 часа, очистка фоновой задачей
  - Зависимость FastAPI `idempotent(required=True|False)` для подключения к эндпоинтам
- **Не входит:**
  - Дедупликация `submissions` по `eventId` (в [T-114](T-114-mocks-bki-submissions.md))
  - Режим `LOST_RESPONSE` (в [T-106](T-106-mocks-chaos.md))

## Критерии приёмки

- [ ] Все строки таблицы правил из 2.7 покрыты тестами
- [ ] Гонка: два одновременных запроса с одним ключом дают один `2xx` и один `409 IDEMPOTENCY_IN_PROGRESS`, ложных `500` нет
- [ ] Без обязательного ключа эндпоинт отвечает `422 VALIDATION_ERROR`; с необязательным работает и без ключа (каждый вызов новый)
- [ ] Ключ старше 24 часов считается новым (проверка через `APP_TODAY`)
- [ ] Сбой, сработавший до обработчика (`ERROR`, `DOWN`, `429`), ключ не записывает
- [ ] Тесты написаны и зелёные
- [ ] Документация и OpenAPI обновлены, если менялся контракт
- [ ] Запись в журнале
- [ ] Выполнено [определение готовности](../04-definition-of-done.md) (линтеры, PR по шаблону, статус задачи обновлён)

## Тесты

pytest с настоящим Postgres: последовательные и параллельные повторы (`asyncio.gather`), расхождение тела, брошенный ключ, истечение срока. Property-тест: для любой последовательности повторов результат один.

## Заметки для реализации

- Запись ключа и вставка в «в работе» должны быть атомарными (уникальный индекс + `INSERT … ON CONFLICT`), иначе гонка даёт ложные `409` и `500` — именно их спецификация запрещает.
- Хеш тела считать от канонического JSON (отсортированные ключи), иначе порядок полей даёт ложное расхождение.
- Этот механизм позже проверяют хаос-тесты `H-06`, `H-07` ([70-06](../../70-quality/06-resilience-and-load.md)).
