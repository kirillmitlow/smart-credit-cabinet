## Цель

Одним запросом проверяются все участники заявки по перечню Росфинмониторинга, платформе «Знай своего клиента» и внутреннему стоп-листу. Из этого строится стоп-фактор `AML_LIST`.

## Входит / не входит

- **Входит:**
  - `POST /api/v1/compliance/screening`: список ИНН с ролями (`COMPANY`, `DIRECTOR`, `FOUNDER`…) → результат по каждому: `aml`, `zsk` (уровень риска), `internalStopList`
  - Справочники комплаенса внутри `mock-bank-core` и поле `compliance` в админ-теле `PUT`
  - Блок `meta` (`source: COMPLIANCE`); ИНН, которого нет в справочниках, — чистый результат (`200`)
- **Не входит:**
  - Сценарий `t-aml` ([T-135](T-135-mocks-technical-scenarios.md))

## Входные документы

- [Спецификация моков](../../../specs/mocks.md), раздел 7.6, 7.7, 8.3

## Критерии приёмки

- [ ] Пример 7.6 воспроизводится; чистый ИНН даёт чистый результат
- [ ] Проверка массива из нескольких участников возвращает результат по каждому
- [ ] Пустой список или неверный ИНН в списке — понятный `422`/`400`
- [ ] OpenAPI описывает запрос и ответ
- [ ] Тесты написаны и зелёные
- [ ] Документация и OpenAPI обновлены, если менялся контракт
- [ ] Запись в журнале
- [ ] Выполнено [определение готовности](../04-definition-of-done.md) (линтеры, PR по шаблону, статус задачи обновлён)

## Тесты

Тесты роли: чистая компания, директор в перечне, компания в стоп-листе, смешанный список.

## Заметки для реализации

- Директор и учредители уходят в проверку все — это делает сценарий при записи ([T-125](T-125-mocks-expand-other-systems.md)), а не мок.
