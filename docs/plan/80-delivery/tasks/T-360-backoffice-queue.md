## Цель

Андеррайтер видит заявки, которые ждут решения: компания, запрос, «почему здесь», рекомендация ядра; список обновляется по SSE.

## Входит / не входит

- **Входит:** `GET /backoffice/queue` через `queries.py` модуля `backoffice` (исключение R5), фильтры статус/продукт, сортировка «старые сверху»; колонки: номер и время ожидания, компания (клиент банка или нет), запрос, коды причин ручного рассмотрения с короткими названиями, рекомендация ядра; отметки «получен документ», «клиент ответил», «источник недоступен»; автоотказы в очередь не попадают.
- **Не входит:** карточка ([T-361](T-361-backoffice-card.md)).

## Реализация B, 23.10

GET /backoffice/queue: отдельная банковская модель, status (по умолчанию MANUAL_REVIEW), productCode, limit 1…100 (20 по умолчанию), непрозрачный курсор с привязкой к фильтру. Старые сверху по входу в текущий статус, затем UUID. По другим статусам показываются только заявки, прежде бывшие в ручном рассмотрении; автоматические стоп-отказы исключены даже при ошибочном текущем статусе. Последний ENGINE-снимок выбирается один раз на заявку, а не размножает строки при повторных расчётах.

Чтение чужих таблиц только в backoffice/queries.py через статические Core-проекции (R5), без записи и импорта внутренних моделей. Причины — trace 11.routing.detail.manual; пояснения берутся из сохранённого снимка. Рекомендация возвращается без выдуманной подстановки: при PIPELINE_ERROR без решения она null. Поле версии готово для будущих действий.

Ожидание и overdue считает сервер через часы приложения. Календарь MVP для подсветки: 24 часа по будням, выходные исключены; часы работы банка и государственные праздники не моделируются. Это подсветка очереди, таймеры закрытия заявки не запускаются. CLIENT_ANSWERED берётся из версии INFO_PROVIDED; технические сбои — из причин и флагов. documentReceived=null означает, что T-332/T-350 ещё не подключены; отсутствие данных не выдаётся за отсутствие документа.

Проверки семи ручных персон используют реальные результаты ядра на утверждённых входах оракула, не только подготовленные JSON. Живой путь через моки/документы ещё требует задач A. SSE — общий T-352, сейчас модуль notifications пустой; этот PR создаёт API, T-429 подключит готовый useEventStream и резервный опрос. Не объявлять push-поток реализованным этим endpoint.
