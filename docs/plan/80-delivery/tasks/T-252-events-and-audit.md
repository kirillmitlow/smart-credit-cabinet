## Цель

Все изменения заявки записываются одной функцией в той же транзакции, остальные действия — через `audit.record`; журналы нельзя править (триггер).

## Входит / не входит

- **Входит:** `record_event(...)` с полями `kind`, `from/to`, `step_code`, `actor`, `reason_code`, `payload`, `request_id`; `id` последовательный (он же `Last-Event-ID`); таблица `audit_log` и функция `audit.record(...)` для входов, ролей, документов, действий банка и демо; триггер, запрещающий `UPDATE/DELETE` для `application_events`, `audit_log` (а также `decisions`, `decision_reasons`, `source_snapshots` — по мере их появления); очистка только `TRUNCATE` в демо-сбросе; тест, запрещающий прямой `INSERT` в эти таблицы мимо функций.
- **Не входит:** цепочка хешей ([T-395](T-395-audit-hash-chain.md)); проекция в таймлайн ([T-255](T-255-application-timeline.md)).

## Критерии приёмки

- [ ] Попытка `UPDATE/DELETE` журнала отклоняется (тест)
- [ ] В `payload` и `details` нет персональных данных, кодов подписи и тел документов
- [ ] Запись события и смена статуса откатываются вместе
- [ ] Время записи берётся из `clock`
- [ ] Тесты написаны и зелёные (`make check`)
- [ ] Документация и OpenAPI обновлены, если менялся контракт
- [ ] Запись в журнале

## Тесты

integration: триггеры, откат; unit: форма записей.

- Прямой `INSERT` мимо функций ловит тест, ищущий такие вызовы ([50-10](../../50-architecture/10-audit-and-observability.md), заметки).
