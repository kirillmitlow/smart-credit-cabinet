## Цель

После `docker compose up` на пустых базах персоны появляются сами: жюри ничего не запускает руками. Эта задача — базовая часть из 10.6: запись встроенных сценариев и применение при пустых моках.

## Входит / не входит

- **Входит:**
  - При старте до статуса `ready`: миграции; запись встроенных сценариев из кода в свою базу (нет в базе — добавить); сверка с моками (`GET /admin/scenarios`) и применение там, где данных нет
  - Первая попытка закончена → `GET /health/ready` отвечает `200`, даже если часть сценариев упала (они помечены `FAILED`, повтор — в [T-129](T-129-mocks-resync-reset.md))
  - Compose-зависимость: `api` ждёт `mock-scenarios: service_healthy`
- **Не входит:**
  - Переприменение по версии и по смене месяца, фоновые повторы, `POST /scenarios/sync`, `POST /scenarios/reset` ([T-129](T-129-mocks-resync-reset.md))

## Тесты

Интеграционный тест на compose: пустые базы → заполнено; перезапуск `mock-scenarios` → данные не тронуты; один мок остановлен при старте → `ready`, `FAILED`.

## Заметки для реализации

- Данные записываются из сохранённого `expanded`, а не разворачиваются заново, когда база мока пересоздана (описано в [T-129](T-129-mocks-resync-reset.md)); здесь достаточно первого применения.

22.10: startup.initialize под locked_session получает инвентарь четырёх ролей,
создаёт новые BUILTIN и применяет их, существующие записи не обновляет по версии
или месяцу. Для пустой роли использует только сохранённый expanded; остальные
роли и их RUNTIME не трогает. При неизвестном инвентаре PUT не выполняется:
иначе временный сбой GET мог бы стереть существующие данные.

Новая персона при недоступном моке получает FAILED; существующая при неполной
сверке — PARTIAL. Первое обследование роли делается один раз, без N одинаковых
таймаутов на N персон. После первой попытки ready разрешён; последующие повторы,
версии, месяц, sync/reset — T-129. CUSTOM с кодом встроенного сценария сохраняется
и не переписывается; конфликт отмечается в журнале процесса.

Проверки: 702 passed, 94,70%; make check зелёный (392 быстрых, mypy 107 файлов).
На этом Mac первый старт mock-scenarios до ready — 0,99 с при уже поднятых
четырёх моках, перезапуск — 1,28 с. Это не время сборки/старта всего будущего
compose с api и интерфейсом. Отдельный реальный контейнерный тест подтвердил
ready при остановленном БКИ и сохранение выданного кредита/отчёта при рестарте.

Для T-129/T-138 отдельно проверить аварию посередине восстановления роли с
несколькими субъектами: текущая стартовая инвентаризация проверяет наличие кода,
а не полноту всех субъектов. Нельзя считать этот крайний случай уже проверенным.
