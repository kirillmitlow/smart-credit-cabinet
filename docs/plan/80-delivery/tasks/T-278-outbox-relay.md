## Цель

Сообщения во внешние системы пишутся в одной транзакции со сменой статуса и доставляются «хотя бы раз» с ключами идемпотентности: ни одно не теряется, ни одно не задваивается по результату, порядок по заявке сохраняется.

## Входит / не входит

- **Входит:** API записи (`enqueue_outbox(aggregate_id, event_type, target, payload, key)`), статусы `PENDING/SENT/FAILED`, уникальность ключа; `outbox.relay`: выборка `SKIP LOCKED` с арендой, берём запись только если нет более ранней неотправленной по тому же `aggregate_id`; толчок после коммита + страховка beat каждые 30 с; паузы 5 с → 15 → 45 → 2 мин → 5 мин с разбросом; после 30 попыток или 24 ч → `FAILED` с записью в аудит; при открытом предохранителе сообщение откладывается без траты попытки; регистрация обработчиков модулями при старте (shared их не знает).
- **Не входит:** конкретные обработчики БКИ ([T-279](T-279-outbox-bureau-handlers.md)) и АБС ([T-342](T-342-disbursement-workflow.md)); кнопка ручного повтора ([T-365](T-365-backoffice-outbox-retry.md)).

## Критерии приёмки

- [ ] Два ретранслятора одновременно не берут одно сообщение (интеграционный тест)
- [ ] Property-тест: при любом порядке сбоев сообщения по одной заявке уходят по порядку и без дублей на стороне мока
- [ ] Откат транзакции откатывает и запись outbox
- [ ] `FAILED` видно в метрике `outbox_dead_total` и в демо-панели, ручной повтор возможен
- [ ] Тесты написаны и зелёные (`make check`)
- [ ] Документация и OpenAPI обновлены, если менялся контракт
- [ ] Запись в журнале

## Тесты

integration (Postgres + Redis) + property на сбоях; chaos с `LOST_RESPONSE`.

## Заметки для реализации

- Ключ идемпотентности строится из бизнес-данных, не случайно ([50-08](../../50-architecture/08-integration-adapters.md)); мок помнит ключ 24 часа — отсюда предел в сутки.
- Подходит для передачи в GPT-6 Astra: конкурентность и порядок.
