## Цель

`api` умеет открывать транзакцию сервисом (R7), применять миграции при старте без гонки двух экземпляров и тестироваться на настоящем Postgres. Общие таблицы платформы (`outbox`, `idempotency_keys`) создаются первой миграцией.

## Входит / не входит

- **Входит:** синхронный SQLAlchemy 2 + psycopg 3, фабрика сессий, помощник «сервис открывает транзакцию», UUID v7 как идентификатор, `created_at/updated_at`; Alembic: первая миграция с `outbox` и `idempotency_keys` (поля из [50-06](../../50-architecture/06-data-model.md)); автоприменение при старте под advisory lock Postgres; тест «модели SQLAlchemy = схема после миграций», тест `upgrade` → `downgrade` на шаг → `upgrade`; подключение общей обвязки Testcontainers из [T-516](T-516-testcontainers-harness.md) (Postgres 17, Redis): фикстуры `api`, откат транзакции между тестами (D-088, Q-104).
- **Не входит:** таблицы других модулей (каждая создаётся в задаче своего владельца); триггеры неизменяемости журналов ([T-252](T-252-events-and-audit.md)).

## Критерии приёмки

- [ ] Два параллельно стартующих процесса `api` не ломают друг друга: второй ждёт блокировку и видит готовую схему (интеграционный тест)
- [ ] `/health/ready` из [T-209](T-209-health-endpoints.md) будет проверять версию миграций: заложена функция «текущая ревизия = head»
- [ ] Статусы и коды хранятся строками с `CHECK`, не `ENUM` Postgres ([50-06](../../50-architecture/06-data-model.md), заметки)
- [ ] Фикстуры работают одной командой `make test` на любом ПК с Docker, без ручного подъёма БД
- [ ] Тесты написаны и зелёные (`make check`)
- [ ] Документация и OpenAPI обновлены, если менялся контракт
- [ ] Запись в журнале

## Тесты

integration: миграции с нуля и откат, гонка двух стартов, откат транзакции в фикстуре.

## Заметки для реализации

- Тесты ядра (`decisioning`) БД не используют и не должны её требовать.
- Таблицу принадлежности «таблица → модуль» (R5) завести сразу как словарь в `shared`: тест «каждая таблица числится ровно за одним модулем» заработает по мере появления таблиц.
