## Зачем

План написан, код пишут два ИИ-агента посменно. Документ отвечает на вопрос «кто берёт какую задачу и как не мешать друг другу». Протокол смены ([протокол смены](../00-meta/03-collaboration-protocol.md)) остаётся главным; здесь его продолжение для кода.

## Кто есть кто

| Кто | Роль в реализации |
|---|---|
| **Claude Code** (агент A) и **Codex** (агент B) | Равноправные сменщики. Закрепления «моё/твоё» нет: задачу берёт тот, кто активен и у кого есть лимиты (D-005) |
| **GPT-6 Astra** (через Codex) | Только задачи с 🧠, у которых есть самодостаточная карточка. Лимиты малы, поэтому одна задача за раз |
| **Субагенты** | Параллельные исполнители независимых задач внутри сессии агента (D-00D). Получают только карточку задачи и список файлов |
| **Пользователь** | Принимает решения по технологиям и продукту, даёт согласие на слияние в `main`, выдаёт доступы, отвечает на вопросы |
| **Команда (4 человека)** | Заданий в разработке не имеет; делает два дела по D-009 (ниже) |

## Правило «одна задача — одна ветка — один PR»

1. **Карточка.** Работа идёт только по карточкам `tasks/T-NNN-*.md`. Нет карточки — сначала создаём её (в диапазоне своей зоны номеров) или записываем вопрос.
2. **Ветка = замок.** Перед началом выполните `git ls-remote --heads origin 'feat/*'` и убедитесь, что ветки с именем из карточки нет. Первая запушенная ветка занимает задачу; второй агент берёт другую. Имя ветки уже написано в карточке.
3. **Один PR на карточку.** Заголовок: `[A] T-NNN Что сделано` (или `[B]`). В теле: ссылка на карточку, что сделано, как проверить, какие критерии приёмки закрыты.
4. **Не расширять.** Нашли соседнюю проблему — новая карточка или вопрос в [реестре вопросов](../00-meta/06-open-questions.md). Размер PR ориентировочно до 400 строк без сгенерированного кода.
5. **Статусы карточки.** `TODO` → `IN_PROGRESS` (ветка запушена) → `REVIEW` (PR открыт, CI зелёный) → `DONE` (влит в `main`) или `BLOCKED (Q-NNN)`. Статус меняется в самом PR задачи, чтобы не было правок общих файлов отдельными коммитами.
6. **Порядок выбора.** Сначала задачи ближайшей вехи ([80-02](02-schedule.md)), внутри вехи Must раньше Should и Could, затем по зависимостям; задача с невыполненной зависимостью не начинается.
7. **Контракты.** OpenAPI, модель данных, `policy`, статусы заявки и контракты моков меняются только через решение ([протокол смены](../00-meta/03-collaboration-protocol.md), правило 2). Правка схемы без записи решения — дефект PR.

## Когда активны оба агента одновременно

Codex работает на другом ПК (D-00A), поэтому окна могут пересекаться.

| Ситуация | Правило |
|---|---|
| Разные каталоги (`mocks/` и `api/`, `web/`, `docs/`) | Параллелим свободно; это основной способ ускорения |
| Общие файлы: `docker-compose.yml`, `Makefile`, `.env.example`, `AGENTS.md`, `.github/workflows/`, `THIRD_PARTY_NOTICES.md` | Правит задача, которой они принадлежат ([T-502](tasks/T-502-compose-main.md), [T-500](tasks/T-500-monorepo-skeleton.md), [T-505](tasks/T-505-env-example.md), [T-509](tasks/T-509-ci-skeleton.md), [T-524](tasks/T-524-third-party-notices.md)); остальным нужны добавления делают маленьким PR в сторону владельца или в конце своего PR отдельным коммитом. Перед PR `git fetch` и `git rebase origin/main` |
| `08-handoff.md` и журнал | Handoff перезаписывает агент, уходящий с последней смены; при пересечении каждый пишет свой блок «Дорожка A / Дорожка B», слияние делает тот, кто заканчивает позже. Журнал только дополняется |
| Спорное решение | Не спорим в коде: записываем вопрос и делаем то, что от него не зависит |

## Передача смены в реализации

Дополняет [протокол смены](../00-meta/03-collaboration-protocol.md). В `08-handoff.md` на момент передачи указываются: номер и ветка текущей карточки, что из критериев приёмки закрыто, команда, которой воспроизводится следующий шаг (например, `make check`, конкретный тест), что красное в CI и почему, какие карточки уже запушены. Незаконченное — коммит `[A] wip: …`. Пушим только рабочие ветки (`feat/*`, `chore/*`, `test/*`, `plan/*`); в `main` попадаем через PR с согласия пользователя (D-00E).

## Параллельные субагенты: когда и как

- **Когда:** независимые карточки в разных каталогах (например, четыре роли моков после общего слоя, [80-02](02-schedule.md)), независимые проверки (ссылки, лицензии), чтение документов для сводки.
- **Как:** основной агент выдаёт карточку и ветку, субагент делает работу и возвращает результат; PR открывает основной агент, проверив diff и прогнав `make check`.
- **Чего нельзя:** передавать субагенту решения о контрактах, слияние в `main`, действия вне репозитория.

## Чего агентам нельзя

- Пушить в `main` и публиковать образы до сдачи (D-083); использовать `git push --force`.
- Менять принятые решения, пороги покрытия и состав CI по своему усмотрению (D-087…D-089).
- Хранить секреты в репозитории, в логах, в тексте PR; добавлять в образы `docs/` и PDF кейса (D-001, D-081).
- Выдумывать недостающее: дыра в документе — вопрос, а не догадка.

## Ритм дня

| Момент | Что делаем |
|---|---|
| Начало смены | `git switch main`, `git pull`, чтение [handoff](../00-meta/08-handoff.md), последних записей журнала, проверка красного `main` (его чинят первым) |
| В течение смены | Карточка за карточкой; после каждого PR — запись в журнал |
| Контрольные точки K1…K5 | Сверка с [80-02](02-schedule.md), пересчёт коэффициента часов |
| Конец смены | Перезаписать `08-handoff.md`, запись в журнал, обновить статусы карточек и 80-01 |

## Заметки для реализации

- Шаблон карточки [templates/task.md](../00-meta/templates/task.md) расширен двумя строками (приоритет и веха) и пометкой 🧠 в заголовке; предложено внести их в шаблон.
- В разных зонах номеров работают разные агенты: T-100…T-199 моки, T-500…T-599 инфраструктура и сдача; T-200…T-499 ядро, `api`, фронт, ИИ. Номера не пересекаются; новые карточки берут следующий свободный номер своей зоны.
