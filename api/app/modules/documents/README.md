# Публичный интерфейс документов

Первый пакет T-332: хранение исходных байтов, метаданные и проверка загрузки.
Разбор 1С, подтверждение данных и использование в расчёте — следующие T-330…T-334.
В этом пакете выписка сохраняется в `PENDING`; её числа ещё не участвуют в решении.

## Для владельца банковской зоны

Импорт: `from app.modules import documents`. Транзакцию держит вызывающий.
`Access(user_id, company_ids=(), bank=False)` строится **на сервере из проверенной
сессии**, а не из входных данных. Для банковского чтения — `bank=True` после
обычной проверки актуальной банковской сессии. Клиентские `company_ids` должны
содержать только разрешённые компании без общей роли поручителя.

| Функция | Результат |
|---|---|
| `get_metadata(session, access, document_id)` | Метаданные одного документа, чужой → 404 |
| `list_metadata(session, access, application_id)` | Метаданные файлов заявки; байты не загружаются |
| `as_dict(document)` | Клиентская проекция с видом, происхождением, хешем и состоянием обработки |
| `verified_content(session, access, document_id)` | Метаданные и исходные байты после сверки размера и SHA-256 |

Прямые импорты `documents.models` и чтение/запись таблиц из backoffice не нужны.
Сохранённый исходник неизменяем; отмена при замене видна по `cancelled_at`.
Физически `document_blobs` хранит bytea отдельно от метаданных. `FileStore` имеет
`put/get/delete`; прикладное чтение идёт через `verified_content` с проверкой прав.
Новые договоры и графики создаются как PDF с кириллицей при принятии предложения.
Исходник и его SHA-256 сохраняются атомарно с договором; подпись привязана к байтам PDF.
Снимок JSON сохраняет расчётные условия; чтение и выдача сверяют обе связи и подпись.
Старые подписанные JSON-договоры остаются доступны без пересоздания.

## HTTP

| Ручка | Доступ |
|---|---|
| `POST /documents` | Только клиент; multipart: `applicationId`, необязательные `taskId`/`replacesId`, `kind`, `file`. Обязателен `Idempotency-Key` |
| `GET /documents?applicationId=...` | Файлы заявки своей компании |
| `GET /documents/{id}` | Своя компания; для банковской сессии явно `?zone=bank` |
| `GET /documents/{id}/download` | Те же права; attachment (для PDF `?preview=true` — inline), nosniff, private/no-store |

Типы загрузки: `BANK_STATEMENT_1C`, `CONTRACT`, `FINANCIALS`, `OTHER`.
Выписка — до 5 МиБ, PDF — до 10 МиБ, до 30 страниц без шифрования; содержимое
проверяется независимо от имени и Content-Type. Суммарно 50 МиБ и 10 файлов на
заявку, включая заменённые исходники. Лимиты в настройках могут быть только ниже
предельных. Имена очищаются и никогда не становятся путями. Загрузка читается
потоково; при превышении лимита следующие порции не читаются.

При `NEEDS_INFO` нужна открытая задача DOCUMENT/CONFIRM_REVENUE именно этой заявки
и право на неё. В DRAFT задача необязательна. Банк через клиентскую ручку не пишет.
Одна транзакция: исходник, метаданные, отмена прежнего, аудит и ключ повтора.
Сбой откатывает всё; повтор того же ключа не создаёт второй файл. Изменение тела
при том же ключе — 409. Смена членства компании действует без повторного входа.

HTTP-сборка в `app.documents_http` / `app.document_actions` соединяет публичные
интерфейсы auth, applications и documents, как `app.wiring`. Нижний модуль
documents не импортирует владельцев заявок/пользователей или банковскую зону.
Операция держит ограждение компании во время чтения файла и записи. Сброс компании
сначала собирает её document/blob IDs, затем удаляет только их, до tasks/applications.
В сообщениях об ошибках и аудите нет исходного текста, назначения платежей или cookie.

## Чистый парсер выписки 1С (T-330)

Публичные функции: `parse_statement(content, expected_inn, as_of=...)` и
`validate_statement_set(results)`. Дата передаётся из часов приложения; парсер
не обращается к БД, сети, внешним процессам или моделям. Возвращает неизменяемый
`ParsedStatement`; `as_dict()` готов для JSON и сохраняет SHA-256 и provenance.

Поддерживается профиль 1.03, Windows-1251 и резервный UTF-8. Секции, счета,
владелец, проведённые даты, дубликаты и остатки проверяются до суммирования.
Исходные деньги читаются через Decimal, затем точно суммируются в копейках;
целые рубли округляются один раз на выходе по ROUND_HALF_UP. Точные копейки
остаются в результате: округлённые части не всегда складываются в округлённый итог.

Полным считается месяц, целиком покрытый всеми загруженными счетами и закончившийся
до текущего месяца приложения. Нужны хотя бы три таких месяца. Неполные месяцы
помечены `complete=false` и не должны повышать средние. Пропущенные дни и неоднозначные
пересечения одного счёта требуют непротиворечивого источника; отсутствие операций
в полностью покрытом месяце даёт нулевой оборот, отсутствие покрытия — не даёт.
Необязательные итоговые поля 1С не выдумываются: при их отсутствии вычисленные
обороты возвращаются с предупреждением CONTROL_TOTALS_MISSING.

Собственные переводы между загруженными счетами отражаются по обеим сторонам,
но помечены OWN_TRANSFER и исключены из кандидатов поступлений от бизнеса.
**Парсер не подтверждает выручку.** Внешние поступления, включая возможные кредит,
взнос владельца и возврат, остаются `ambiguousReceipts` с предупреждением
UNCLASSIFIED_RECEIPTS. Одного назначения платежа недостаточно для классификации;
T-333/T-334 должны получить подтверждение перед использованием этих сумм в решении.
Назначения не попадают в JSON-результат, исключения и логи: аудит ссылается на
сохранённый исходник по SHA-256 и на хеши операций.

При нескольких документах обязательно вызвать `validate_statement_set` **до**
агрегации: одинаковый исходник учитывается один раз; разные файлы с пересечением
периода одного счёта отклоняются, смежные остатки проверяются. Метод расчёта
выручки, НДС и денежного потока остаётся в decisioning; здесь он не дублируется.

Корпус и точные ожидаемые суммы: `tests/fixtures/statements/README.md`.
Включение источника в решение T-334 — отдельный этап. Контракт HTTP и схема БД
этими пакетами не меняются.

## Фоновая обработка (T-333)

Загрузка ставит `documents.parse_statement` после коммита; сообщение содержит только ID.
`app.document_tasks` соединяет публичные интерфейсы модулей, worker регистрирует задачу.
Мягкий лимит 55 с, жёсткий 60 с. Смысловая ошибка сохраняет FAILED/машинный код и
оригинал; неизвестная ошибка — PARSE_FAILED без текста исключения, таймаут — PARSE_TIMEOUT.
Сбой БД откатывает результат, задача повторяется. Beat раз в минуту подбирает незавершённые
документы, включая потерянный толчок в брокер после коммита. Закрытые заявки/задачи пропускает.

Порядок блокировок: ограждение сброса компании → заявка → документ. Сам парсер не ходит
в сеть; ограниченный разбор и одно событие результата/аудит фиксируются одной транзакцией.
Повтор или конкурентная доставка не создаёт второго события. Сброс не пересекается с
обработкой; запоздавшая задача по удалённому ID ничего не восстанавливает. Отзыв заявки
либо происходит до обработки (SKIPPED), либо после её коммита; закрытая заявка не оживает.

Клиент опрашивает список только пока есть незавершённые файлы, видит период/ошибку и может
заменить файл с сохранением старого. До PARSED ответ по документной задаче не отправить;
добавление PDF рядом не обходит проверку неудачной выписки. PARSED означает проверенный
формат и обороты, не подтверждённую выручку. `confirmedAt` остаётся пустым до T-334.
