# Технический протокол

## Границы эксперимента

Сравниваются способы заполнить шесть перечисленных в `schema.json` слотов. Ни в промптах, ни в кандидатах нет списка банковских продуктов. Сумма обрабатывается отдельным детерминированным парсером. Данные содержат 60 dev-, 90 test- и 42 отдельно написанных опорных фразы. Используются только тексты; отрасль, стиль, id и метки модель не видит.

Это сравнение готовых **подходов**, а не одинаково обученных архитектур: kNN получает 42 опорных примера, supervised-классификатор обучается на dev, zero-shot кандидаты используют описания вариантов без размеченных демонстраций. Ограниченный поиск настроек не доказывает, что найден максимум возможностей каждого кандидата.

Test не используется для выбора k, температуры, порога, эпох или промпта. До финального test сделаны технические dev-прогоны: проверены адаптеры, затем исправлен бюджет вопроса Laya и окончательно зафиксирован код. Финальная фиксация — `results/evaluation_seal.json`: SHA данных, настроек и исполняемого кода с lock-файлами. В каждом опубликованном test-прогнозе сохранены все варианты вероятностей, исходные оценки и фактическое решение о подстановке. Повторное чтение CSV для анализа не является повторным инференсом.

## Оценки вариантов

* **Эмбеддинги:** CLS для rubert-tiny2, masked mean для E5/USER/USER2, затем L2-нормализация. Указанные авторами префиксы записаны в `candidates.json`. Для каждого варианта каждого слота берутся k самых близких опорных примеров с этой меткой, их cosine similarity усредняется. k выбирается из {1, 3} по среднему macro-F1 шести слотов на dev. Если примеров класса меньше k, используются все имеющиеся.
* **NLI:** для каждой пары «текст, описание варианта» используется `entailment_logit − logsumexp(other_logits)`. Никакая метка не выбирается по названию банковского продукта.
* **Кросс-энкодер:** исходный logit релевантности пары «текст, описание варианта».
* **Laya:** шесть `choice`-вопросов с русскими инструкциями и описаниями. `head_max_len=512`, `max_len=1024`. Стандартные 256 токенов обрезали инструкции. Внутренний предел SDK в 48 токенов на один вариант сохранён; это ограничение адаптера. Используются публичные probabilities SDK, округлённые до четырёх знаков; перед логарифмом нули заменены на 1e-8. Это может ограничивать точность последующей калибровки.
* **GLiNER:** один вызов с шестью классификациями. Чтобы получить вероятности всех вариантов, включён возврат нескольких меток с нулевым отсечением, но явно задана взаимоисключающая softmax-активация. Поэтому это не независимые sigmoid-вероятности и не отбор по внутреннему порогу GLiNER. Перед логарифмом применяется floor=1e-12.
* **Qwen:** шесть отдельных вопросов, фиксированные варианты A…F, thinking выключен. Ответ — ровно один токен с буквой. Оценка — log-likelihood этой буквы в позиции ответа. Общий член нормировки по словарю сокращается при softmax по допустимым буквам, поэтому достаточно финальных logits этих токенов. Ответы не генерируются и не сэмплируются. Пакетируется до двух вопросов одной фразы, но никогда разные клиентские фразы. Порядок вариантов и verbalizer не перебирались, их возможное смещение — ограничение.

Максимальная длина обычных энкодеров — 192 токена для коротких клиентских текстов и пар. Qwen получает полный вопрос и варианты; обрезания через этот предел нет. Laya/GLiNER используют собственные схемные ограничения. Производительность поэтому сравнивает полные исследуемые методы, а не только одинаковые матричные операции.

## Дообучение rubert-tiny2

Общий BERT-энкодер и шесть линейных голов над CLS; обучаются все параметры энкодера. По 20 эпох, batch=8, AdamW, LR энкодера 3e-5, голов 1e-3, weight decay 0.01, gradient clipping 1.0. Loss — среднее шести cross-entropy без весов классов. Early stopping и подбор эпох не применяются.

Dev-прогнозы для калибровки получены трёхчастным out-of-fold разбиением, стратифицированным по purpose: каждый dev-текст оценивает модель, обученная на других 40 dev-фразах. Seeds разбиения 17, обучения 17/18/19. Финальная модель обучена на всех 60 dev-фразах с seed=17. Разница размера обучения 40→60 может менять распределение уверенности; перенесённые OOF-пороги не являются гарантированно откалиброванными для финальной модели. Веса checkpoint исключены из git и воспроизводятся скриптом.

## Калибровка и отказ от подстановки

Для каждого кандидата и слота отдельно выбирается одна температура по минимуму NLL на dev: 160 геометрически распределённых значений от 0.005 до 20. Входом служат оценки выше; выход — нормированная softmax-вероятность по всем вариантам слота.

Далее перебираются наблюдаемые dev-уверенности `max(p)`. Выбирается порог с наибольшим количеством подстановок, при котором **не меньше пяти** dev-ответов подставлены и их точность ≥95%. Предсказанный UNKNOWN всегда означает уточнение кнопками, даже при p=1. Если подходящего порога нет, threshold=1.01 отключает подстановку слота. OTHER для purpose — полноценная метка, поскольку UNKNOWN в схеме этого слота нет.

Температура и порог подбираются на одних 60 dev-примерах; это допускает переобучение настройки. У fine-tuned кандидата сами прогнозы OOF, но отдельной независимой calibration-части нет. Итоговая проверка — 90 test-фраз с неизменёнными dev-порогами. Провал 95% на test публикуется как провал, а не исправляется новым порогом. Test-кривая risk/coverage сохраняется только для диагностики.

## Метрики

Обычная accuracy и macro-F1 считаются по всем фразам, включая UNKNOWN, macro-F1 — по полному списку допустимых меток с zero_division=0. ECE — десять равных диапазонов уверенности от 0 до 1, взвешенное по количеству ответов абсолютное расхождение confidence и accuracy. `reliability.csv` содержит и пустые диапазоны.

Selective accuracy — верные подстановки / все подстановки. Coverage — все подстановки / все вопросы, то есть /540 для 90 фраз и шести слотов. Это не доля полностью заполненных анкет. UNKNOWN не повышает coverage. Средние accuracy/F1/ECE — среднее шести слотов; основная итоговая selective accuracy объединяет подставленные ответы всех слотов. В CSV также есть среднее по активным слотам, число подстановок, выдуманные известные значения при эталоне UNKNOWN и интервалы Уилсона. Обычная accuracy может быть высокой за счёт отсутствующих полей, поэтому она не является главным критерием.

Для purpose полностью сохранена матрица 6×6. В отдельной критической таблице для каждой истинной метки DEFERRED_PAYMENT_ORDER и CASH_GAP показаны оба этих предсказания **и уходы в остальные классы**, чтобы не скрывать ошибки вне среза 2×2.

Сумма сравнивается по точному совпадению int/null. Отдельно показаны точность среди названных сумм и лишние извлечения, чтобы много null не создавало иллюзию высокого качества.

## Скорость, память и ограничения воспроизведения

CPU, float32, PyTorch intra-op=4 и inter-op=1. Ни CUDA, ни MPS не используются. Каждый кандидат — отдельный процесс. Три прогревочные фразы берутся только из dev. Одна фраза замеряется один раз со всеми шестью слотами; затем считаются p50/p95 по 90 фразам. Подбор температуры, запись CSV, парсер суммы и таблица выбора продукта в тайминг модели не включены. Парсер измеряется отдельно в `amount_test.csv`; кода таблицы продуктов в исследовании нет.

Загрузка — чтение локального checkpoint, создание модели и, для kNN, подготовка 42 опорных эмбеддингов. Импорты Python и сеть исключены. Cold filesystem cache не сбрасывается: это локальная загрузка с возможным файловым кешем ОС. RAM — пиковый RSS процесса за весь отдельный test-запуск, включая загрузку и прогрев. Диск — фактические скачанные файлы модели; окружения Python и общий кеш uv не входят. Для fine-tuned учтены и исходный энкодер, и исследовательский checkpoint; в минимальной поставке можно избежать дублирования исходных весов.

Стенд — Apple M4, 10 логических CPU, 24 ГиБ RAM, macOS, Python 3.13.7. Это CPU-замер, **не проверка на офисном x86-ПК с 8 ГБ**. Пиковый RSS помогает отсеять тяжёлые модели, но не доказывает работу с конкретным ограничением общей памяти. Другие приложения, ОС и архитектура CPU могут менять задержки; изоляции ядрами и ограничения RAM не делалось. Окончательные test-замеры выполняются последовательно после окончания скачиваний.

Скачивания идут с докачкой через curl. Бюджет одного кандидата — 20 минут; запуск до первого ответа также ограничен 20 минутами. Полный этап одного кандидата дополнительно ограничен часом как исследовательский бюджет. Неуспехи записываются, результаты не заменяются придуманными оценками. Квантизация, ONNX, специализированные x86-ядра и повторные серии задержек в это исследование не входят.
